# Research Report: OpenArtifact – Internal & External Credential Management Architecture

**Date:** 2026-11-23  
**Status:** Research & Analysis only — builds on `docs/research-credential-management-audit.md`  
**Scope:** Architecture for separating Internal vs. External credentials, storage backend abstraction, lifecycle management

---

## 1. Executive Summary

This follow-up research addresses the **precise product requirement**: OpenArtifact needs a central credential management that cleanly separates:

| Category | Examples | Key Difference |
|----------|----------|----------------|
| **Internal Credentials** | MCP Access Tokens, API Access Tokens | OpenArtifact **generates, owns, controls lifecycle** — hash storage, rotation, revocation, expiry |
| **External Credentials** | OpenRouter Key, GitHub PAT, PostgreSQL URL | OpenArtifact **only stores & uses** — encryption, test, update, delete; no generation |

The existing secret store (`SecretStore`, `secrets` table, AES-256-GCM) is a **generic encrypted blob store** — it has no concept of credential types, lifecycle, or ownership. It works perfectly as the **default storage backend** for both categories.

**Core architectural decision:** Build a **single Credential Service** with **two lifecycle implementations** (Internal / External) and a **pluggable storage backend interface** — the secret store remains the default backend; external stores (OpenBao, Vault) can be added later without touching nodes, providers, or executors.

## 3. Internal Credentials – Architecture & Lifecycle

### 3.1 What Are Internal Credentials?

| Property | Detail |
|----------|--------|
| **Generated by** | OpenArtifact (not user-provided) |
| **Examples** | MCP Access Tokens (for external agents), API Access Tokens (for `/api/v1`), future: webhook signing keys, inter-service tokens |
| **Ownership** | OpenArtifact controls full lifecycle |
| **Storage** | **Hash only** (bcrypt/argon2) — plaintext never stored, shown once at creation |
| **Lifecycle** | Create → (optional) Rotate → Revoke → Expire → Purge |

### 3.2 Existing Token Mechanisms to Reuse

| Mechanism | File | Reusability |
|-----------|------|-------------|
| `OPENARTIFACT_API_TOKEN` | `config.py:55`, `security.py:47-72` | **Reference model** — single token, constant-time compare, bearer header + session cookie |
| Session cookie signing | `security.py:86-113` | **Reference model** — HMAC-SHA256 with secret key, time-bound, rotatable |
| OIDC state tokens | `oidc.py:178` | **Reference model** — `secrets.token_urlsafe(32)` for secure random generation |
| MCP server auth | `mcp.py:6-7`, `security.py:194-210` | **Integration point** — `TokenProtected` middleware validates bearer token |

### 3.4 Token Generation & Storage

```python
# openartifact/credentials/internal.py (new)
import secrets
import bcrypt  # or passlib/argon2

TOKEN_PREFIX = "oa_"  # identifiable in logs
TOKEN_BYTES = 32      # 256 bits entropy

def generate_token() -> tuple[str, str]:
    """Returns (plaintext_token, hash). Plaintext shown ONCE."""
    raw = secrets.token_urlsafe(TOKEN_BYTES)
    token = f"{TOKEN_PREFIX}{raw}"
    hash_bytes = bcrypt.hashpw(token.encode(), bcrypt.gensalt(rounds=12))
    return token, hash_bytes.decode()

def verify_token(plaintext: str, stored_hash: str) -> bool:
    return bcrypt.checkpw(plaintext.encode(), stored_hash.encode())
```

**Key points:**
- **Plaintext shown once** at creation (UI: copy button, "I have copied this" confirmation)
- **Hash stored** in `secrets.value` (encrypted blob) — but since we hash *before* encrypting, even DB compromise + key compromise doesn't yield usable tokens
- **Prefix `oa_`** — identifies internal tokens in logs/debugging
- **Rotation** = create new credential (new name or same name with version), keep old valid for grace period, then revoke old

### 3.5 Revocation & Expiry Handling

| Scenario | Behavior |
|----------|----------|
| **Explicit revoke** | `enabled = False` on credential; `SecretStore.resolve()` returns "Secret NAME does not exist" for revoked |
| **TTL expiry** | Background job or on-resolve check: if `expires_at < now`, treat as revoked |
| **Rotation** | Create new internal credential (new name or same name + version suffix); old marked `superseded_by = new_id`; grace period configurable |
| **Running requests** | Stateless — token validated per-request via middleware; revoked tokens fail next request immediately |
| **Audit trail** | New `credential_audit` table: `credential_id`, `action` (created/rotated/revoked/used), `at`, `by`, `ip` |

### 3.6 Integration with Existing Auth

| Component | Current | With Internal Credentials |
|-----------|---------|---------------------------|
| **API token** (`OPENARTIFACT_API_TOKEN`) | Single env var | Becomes first internal credential (type `api_access_token`); multiple tokens possible |
| **MCP server** | Uses same API token | Can have dedicated MCP tokens (type `mcp_access_token`) with separate revocation |
| **Session cookies** | Signed with `secret_key` | Unchanged — separate from credential system |
| **OIDC** | External IdP | Unchanged — internal credentials are for programmatic access only |

## 4. External Credentials – Architecture & Lifecycle

### 4.1 What Are External Credentials?

| Property | Detail |
|----------|--------|
| **Generated by** | External service (GitHub, OpenRouter, PostgreSQL, etc.) |
| **Examples** | OpenRouter API Key, GitHub PAT, PostgreSQL connection URL, HTTP Bearer Token, MCP Auth Token |
| **Ownership** | User provides; OpenArtifact stores & uses |
| **Storage** | **Encrypted** (existing AES-256-GCM via `SecretStore`) — plaintext needed at runtime |

### 5.2 Proposed Storage Backend Interface

```python
# openartifact/credentials/storage.py (new)
from abc import ABC, abstractmethod
from collections.abc import Sequence
from dataclasses import dataclass
from typing import Any

@dataclass
class SecretMetadata:
    name: str
    created_at: datetime
    updated_at: datetime

@dataclass
class SecretValue:
    name: str
    value: str  # plaintext (for internal: not used; for external: decrypted)

class SecretStorageBackend(ABC):
    """Interface for secret storage backends."""
    
    @property
    @abstractmethod
    def name(self) -> str: ...  # e.g., "internal", "openbao", "vault"
    
    @property
    @abstractmethod
    def supports_internal_credentials(self) -> bool: ...
    
    @abstractmethod
    async def list_secrets(self) -> list[SecretMetadata]: ...
    
    @abstractmethod
    async def get_secret(self, name: str) -> SecretValue | None: ...
    
    @abstractmethod
    async def store_secret(self, name: str, value: str, metadata: dict | None = None) -> SecretMetadata: ...
    
    @abstractmethod
    async def delete_secret(self, name: str) -> None: ...
    
    @abstractmethod
    async def resolve(self, names: Sequence[str]) -> dict[str, str]: ...
    
    @abstractmethod
    async def health_check(self) -> bool: ...  # for external backends
    
    @abstractmethod
    async def close(self) -> None: ...
```

### 5.3 Default Implementation (Wraps Existing SecretStore)

```python
# openartifact/credentials/storage.py
class InternalSecretStorage(SecretStorageBackend):
    """Wraps the existing SecretStore — default backend."""
    
    def __init__(self, secret_store: SecretStore):
        self._store = secret_store
    
    @property
    def name(self) -> str:
        return "internal"
    
    @property
    def supports_internal_credentials(self) -> bool:
        return True  # can store hashes
    
    async def list_secrets(self) -> list[SecretMetadata]:
        reads = await self._store.names()
        return [SecretMetadata(r.name, r.created_at, r.updated_at) for r in reads]
    
    async def get_secret(self, name: str) -> SecretValue | None:
        try:
            values = await self._store.resolve([name])
            return SecretValue(name, values[name])
        except SecretResolveError:
            return None
    
    async def store_secret(self, name: str, value: str, metadata: dict | None = None) -> SecretMetadata:
        read, _ = await self._store.put(name, value)
        return SecretMetadata(read.name, read.created_at, read.updated_at)
    
    async def delete_secret(self, name: str) -> None:
        await self._store.delete(name)
    
    async def resolve(self, names: Sequence[str]) -> dict[str, str]:
        return await self._store.resolve(names)
    
    async def health_check(self) -> bool:
        return True
    
    async def close(self) -> None:
        pass
```

    elif settings.credential_storage_backend == "openbao":

### 5.7 Handling Backend Failures

| Scenario | Behavior |
|----------|----------|
| **External backend unavailable at startup** | Log warning; fall back to internal if configured; or refuse startup if external is required |
| **External backend unavailable at runtime** | `resolve()` raises `SecretResolveError` → node fails with clear message; circuit breaker pattern recommended |
| **Backend migration** | Dual-write during transition; read from new, fallback to old; migrate metadata table |
| **Secret name conflicts** | Namespace per backend (e.g., `openbao:MY_SECRET`) or single namespace with backend column in `credentials` table |

### 6.2 Credential → Secret Mapping

| Credential Category | Secret Store Content |
|---------------------|---------------------|
| **External** | Encrypted plaintext (AES-256-GCM) — decrypt at runtime |
| **Internal** | Encrypted **hash** (bcrypt/argon2) — verify at runtime, never decrypt to plaintext |

**Why same `secrets` table?** 
- Executors call `resolve(names[])` → get plaintext values
- For internal: `resolve` returns the **hash** (not usable directly) — but internal credentials are **never resolved by executors**; they're validated by auth middleware
- **Separation:** Internal credentials use dedicated validation path; external credentials use existing `SecretStore.resolve()`

### 6.3 Stable Credential ID

- `credentials.id` (UUID) = stable identifier
- `credentials.name` = human-readable, used in node configs (unchanged)
- **Nodes/providers still reference by name** — zero migration
- Credential ID used internally for FKs, audit logs, API

## 8. Security Considerations

### 8.1 Internal Credentials — Hash-Based Security

| Threat | Mitigation |
|--------|------------|
| DB leak + secret key leak | Hash (bcrypt) stored *before* encryption → attacker gets only hash |
| Token in logs | Never logged; shown once at creation; prefix `oa_` identifies in accidental leaks |
| Brute force | bcrypt rounds=12; 256-bit entropy |
| Replay after revoke | Stateless validation per request; revoked = immediate fail |
| Rotation without downtime | Grace period: old + new valid simultaneously |

### 8.2 External Credentials — Encryption-Based Security

| Threat | Mitigation |
|--------|------------|
| DB leak | AES-256-GCM + HKDF-SHA256 (existing) |
| Secret key leak | Key not in DB; separate from backup |
| Log leakage | Masking in outputs/logs (existing) |
| Code node exfiltration | Inherent — treat "edit actions" = "read all secrets" |

### 8.3 Storage Backend Security

| Backend | Trust Model |
|---------|-------------|
| **Internal (default)** | Full control; encryption + optional hashing |
| **OpenBao / Vault** | External system; OpenArtifact authenticates via token; TLS required; secrets encrypted at rest in Vault |

**Recommendation:** For external backends, **hash internal credentials before sending to backend** — never trust external store with raw tokens.

## 10. Architecture Variants Comparison

### Variant A: Single Credential Service with Two Lifecycle Implementations

```
CredentialService
  ├── InternalLifecycle (generate, hash, rotate, revoke, expire)
  ├── ExternalLifecycle (store, encrypt, test, update, delete)
  ├── TypeRegistry (shared)
  ├── StorageBackend (pluggable)
  └── API (unified)
```

| Criterion | Assessment |
|-----------|------------|
| **Complexity** | Low-Medium — single service, clear separation in lifecycle classes |
| **Modularity** | High — lifecycle implementations independent |
| **Extensibility** | High — new types register with category; new backends implement interface |
| **Security** | Clear — internal uses hash path, external uses encryption path |
| **Migration** | Low — builds on Variant B from first audit |
| **Node/Provider impact** | Zero — unchanged |

### Variant B: Two Separate Services

```
InternalCredentialService    ExternalCredentialService
  ├── generate                  ├── store
  ├── hash                      ├── encrypt
  ├── rotate                    ├── test
  ├── revoke                    ├── update
  └── expire                    └── delete
  (own storage?)              (own storage?)
```

| Criterion | Assessment |
|-----------|------------|
| **Complexity** | Higher — duplicate APIs, duplicate type registry, duplicate storage handling |
| **Modularity** | Forced — but artificial split; both need storage, types, usages |
| **Extensibility** | Lower — cross-cutting concerns (storage backend, type registry) duplicated |
| **Security** | Clear separation but more code surface |
| **Migration** | Higher — two services to build |
| **Node/Provider impact** | Zero |

### Variant C: Credential Service with Pluggable Backends + Separate Token Management

```
CredentialService (metadata, types, API, usages)
  ├── StorageBackend (internal, openbao, vault)
  ├── TokenManager (internal only: generate, hash, rotate, revoke)
  └── Validator (internal: verify hash; external: decrypt)
```

| Criterion | Assessment |
|-----------|------------|
| **Complexity** | Medium — three components but clean separation |
| **Modularity** | Very high — storage, token mgmt, validation all swappable |
| **Extensibility** | Highest — new backend = implement interface; new token type = new TokenManager |
| **Security** | Best — token management isolated from storage |
| **Migration** | Medium — more components but each simpler |
| **Node/Provider impact** | Zero |

### 10.1 Recommendation: **Variant A (Enhanced)**

**Why not B?** Artificial split; both categories need metadata, types, usages, storage, API — duplication without benefit.

**Why not C?** Over-engineered for v1. Token management is simple (generate/hash/verify/rotate); doesn't need separate service. Can extract later if needed.

**Variant A with these concrete choices:**

## 13. Open Architecture Decisions

| Decision | Options | Recommendation |
|----------|---------|----------------|
| **Internal token hash algorithm** | bcrypt (rounds=12) vs argon2id | **bcrypt** — stdlib via `passlib`, proven, simpler |
| **Internal token prefix** | `oa_` vs `oat_` vs none | **`oa_`** — short, identifiable, matches project name |
| **Grace period for rotation** | Fixed (7 days) vs configurable per credential | **Configurable** (default 7) — field in `meta` |
| **External backend config** | Single backend vs multiple simultaneous | **Single active** for v1; multi-backend later |
| **Credential name namespace** | Shared with secrets (1:1) vs separate | **Shared** — simpler, backward compatible |
| **Audit log retention** | Forever vs TTL | **Forever** (small volume); admin can purge |
| **Test execution context** | Run in executor context vs service context | **Service context** — no node limits, simpler |
| **MCP access token scope** | Single token for all MCP vs per-server | **Per-server** (type `mcp_access_token` with `meta.server_url`) |

## 14. Answer to Final Guiding Question

> **How to implement a simple credential management where OpenArtifact manages its own tokens, stores external credentials securely, and can later connect external secret stores like OpenBao — without changing the execution/node architecture?**

### The Answer: Three-Layer Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. CREDENTIAL SERVICE (new, thin)                               │
│    - Metadata, types, lifecycle (internal vs external)          │
│    - API: CRUD, test, rotate, revoke, usages                    │
│    - Delegates storage to backend                               │
└─────────────────────────────────────────────────────────────────┘
                                    │
                    ┌───────────────┴───────────────┐
                    ▼                               ▼
┌─────────────────────────────────┐   ┌─────────────────────────────────┐
│ 2. STORAGE BACKEND INTERFACE    │   │ 3. SECRET STORE (existing)      │
│    - SecretStorageBackend       │   │    - AES-256-GCM encryption     │
│    - InternalSecretStorage      │   │    - HKDF-SHA256 key derivation │
│    - OpenBaoStorage (future)    │   │    - resolve(), masking, uses() │
│    - VaultStorage (future)      │   │    - UNCHANGED                  │
└─────────────────────────────────┘   └─────────────────────────────────┘
```

### What Changes / What Stays

| Component | Change |
|-----------|--------|
| **Nodes / Providers / Executors** | **ZERO** — still reference secret names |
| **Secret Store (`SecretStore`)** | **ZERO** — wrapped, not modified |
| **Database (`secrets` table)** | **ZERO** — same table, same encryption |
| **New: `credentials` table** | Metadata only (type, category, status, FK→secrets) |
| **New: `CredentialService`** | Thin layer: metadata + lifecycle + type registry |
| **New: `SecretStorageBackend`** | Interface; `InternalSecretStorage` delegates to `SecretStore` |
| **New: Internal Token Logic** | Generate → hash → store hash; verify on use; rotate/revoke |
| **New: UI** | Two tabs, picker, category-specific actions |

### Why This Works Long-Term

| Requirement | Solution |
|-------------|----------|
| **Internal tokens self-managed** | `CredentialService` generates, hashes, rotates, revokes; hash stored in secret store |
| **External credentials stored securely** | Existing AES-256-GCM encryption unchanged |
| **External secret stores (OpenBao)** | Implement `SecretStorageBackend`; swap in `app.py` factory; zero node changes |
| **Credential types grow with nodes** | Type registry — each new node type = new credential type with test handler |
| **No breaking changes** | Name-based references preserved; executors call `resolve()` which delegates to backend |
| **Simple UX** | Two tabs (Internal/External) — category determines available actions |
