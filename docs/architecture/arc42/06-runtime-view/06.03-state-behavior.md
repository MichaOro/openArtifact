## 6.3 State Behavior

### Run and stage

A run (`pipeline_runs`, one per artifact) and its stages (`run_stages`) have these states (ADR-013):

```
Run:   (none) ── start ──► running ──┬─ last stage passed ──► done
                              ▲      ├─ missing connection, 1000 steps, nested pipeline cannot go on ──► failed
                              │      ├─ stop ──────────────────────────────────────────────────────► stopped
                              │      └─ container restart ("interrupted") ─────────────────────────► stopped
                              └──────────── start again (from the stored stage and action, or earlier) ──┘

Stage: pending ──► running ──┬─► passed
                             └─► failed
       skipped / passed: set at the start for stages before the start stage
```

- `running` locks the artifact: lane, order, parent and deletion answer `409`; title and body stay editable.
- A second start, or a start during a start, answers `409`. More than `OPENARTIFACT_MAX_CONCURRENT_RUNS` active runs
  answers `429`. There is no wall-clock deadline per run; only the step limit (1000) and a timer node's bound (one day).
- A `waiting` status for human-in-the-loop is planned, not built.

### SQLite WAL mode

```
┌─────────────────────────┐
│      SQLite (WAL)       │
│  readers: concurrent    │
│  writers: serialised    │
│  journal_mode = WAL     │
│  foreign_keys = ON      │
└─────────────────────────┘
```

These two pragmas are the only ones the application sets, per connection (`database.py`); the synchronous mode and
journal limits are SQLite's defaults. The WAL file (`openartifact.db-wal`) holds committed changes that the main file
does not have yet, so a backup uses SQLite's backup API (see the [operations guide](../../../guides/operations.md#backup)).
