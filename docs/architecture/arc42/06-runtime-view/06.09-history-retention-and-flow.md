## 6.9 History, retention and the flow of an execution

The history is the set of `executions` rows. The engine writes it as a by-product of running; reading it is plain
queries; the flow view is computed on read.

### Recording

```
start (6.6)    in the claim transaction: INSERT executions (number, started_by, names, snapshot), status running
each node      INSERT run_node_results (seq, node, outcome, port, exit code, output <= 256 Ki chars, reason, data),
               executions.step_count + 1; if the execution's outputs together exceed 1 Mi chars the oldest outputs
               are replaced by "[output removed: ...]" (the newest stays)
end / stop     ExecutionHistory.close: status, note, finished_at (first end only), final stage and action, step count
               then prune (below); the events go out after the commit
restart        recover() closes executions that were running as stopped, note "Interrupted by restart"
```

Events: `execution.updated` (`{task_id, execution}`, a summary) when an execution starts and whenever its status
changes; `execution.deleted` (`{task_id, id}`) for every deleted one. Steps are not events: the run's `run.updated`
carries the newest steps, the browser asks for the rest.

### Retention (`ExecutionHistory.prune`)

Runs at every start and every end of the artifact's executions (the global rules also when they are saved). There is no
per-artifact policy (ADR-057).

```
the operator's guard:    OPENARTIFACT_EXECUTION_HISTORY_DEFAULT_KEEP as keep_last (50; 0 = keep everything)
for each execution, newest number first (rank 1, 2, ...):
    rank 1                      → kept, always (an artifact shows what happened last)
    running                     → kept, counts toward keep_last
    otherwise                   → deleted if rank > keep_last
delete steps, detach the run row (execution_id = NULL), delete executions; publish execution.deleted
```

Deleting by hand
(`DELETE .../executions/{id}`, `DELETE /api/tasks/{id}/executions`) is not subject to the "newest is kept" rule but never
touches a running execution (`409` for a single one; "clear" skips it). The database runs with `auto_vacuum = FULL`: deleted rows
give their pages back and the file shrinks ([chapter 11](../11-risks-and-technical-debt.md)).

### Flow (`engine/flow.py`)

Only the nodes of action definitions leave steps. Stages, actions without a definition and called pipelines leave
nothing. The flow endpoint therefore *replays* the walk over the frozen snapshot:

```
GET /api/tasks/{id}/executions/{eid}/flow
   read the execution (with its snapshot) and its steps
   fill old snapshots with ids, names, sizes and edge ids (those frozen before the flow existed)
   replay from the entry the execution started at: for each action take On Pass / On Error by what its steps say,
      for an action with a definition hand the next group of steps (a group starts at a trigger step) to it,
      enter a called pipeline as a nested visit
   result: graphs, visits (one pass of the execution through a graph), traversed edges, reached nodes
   stop where the steps run out; the open end is "running" while the execution runs
browser: /artifacts/{ref}/executions/{id} draws the graphs on the editor canvas, read-only, drill into actions and
   nested pipelines, step list with the output loaded on demand (GET .../steps/{step_id}); live via SSE
```

Nothing extra is recorded at run time, so old executions stay drawable. The price: the replay and the engine apply
the same rules in two places (`MAX_ACTIONS` in `flow.py` duplicates `MAX_STEPS`), and they can drift apart if one is
changed ([chapter 11](../11-risks-and-technical-debt.md); `test_execution_flow.py` covers both).

### Global list (`GET /api/executions`)

Keyset paging over `(started_at, id)` descending (index `ix_executions_started_at`, migration 0025): the cursor holds the
last row's pair, so rows inserted or deleted between two page requests neither repeat nor skip rows. Filters are
`status`, `started_by`, `pipeline` (id or part of the stored name), `q`, `since`, `until`, combined with AND; the answer
carries a summary and a total. Maximum page size 200 (default 50).
