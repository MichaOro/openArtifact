## 6.8 Resolving credentials and masking

A node never holds a secret value; it holds a name. The value is looked up when the node runs, handed to the
executor, and removed again from everything the node produced.

```
author (API only)        PUT /api/secrets/{name} or /api/v1/secrets/{name}, body {"value": ...}
                           → 409 unless an API token and an own secret key are set; 422 for bad name or value
                           → AES-256-GCM (8.6) → table secrets (name, encrypted value)
node setting             HTTP node: ${secret:NAME} in the URL path or query, headers, body
                         Execute Command node: setting "secrets", one name per line (max 32)
                           → checked when the node is saved (syntax; not in scheme or host; reserved names rejected)
run time                 executors._with_secrets(names, limits, run):
                           resolver = SecretStore.resolve → decrypt every named secret
                             a missing name or a changed key → the node fails, the reason names the secret, never the value
                           with logging_config.masked_in_logs(values):   # every log line is masked while the node runs
                              HTTP: substitute() puts the values in (the URL part percent-encoded), request is sent
                              Code: values become environment variables NAME=value of the process
                              an exception from the node → fail "The node failed (<class name>)" (no message text)
                           _masked: output, reason and data (JSON, keys too) have every form of every used value replaced by ***
                         engine stores the masked result as a step; events and API responses carry the stored result
```

What "every form" means (`credentials.refs.forms_of`): the value as it is, percent-encoded (`quote` and `quote_plus`), Base64
(standard and URL-safe, with and without padding) and JSON-escaped, longest first. What it cannot catch: a value that
was transformed in any other way (hashed, reversed, split over lines, printed one character at a time). A node that may
read a secret can leak it on purpose; masking protects against accidents and echoes, not against the node's author.

Snapshots (the frozen copy stored with every execution) contain the node's settings, therefore the names and references,
never values. The API shows names and dates of secrets (and `GET /api/secrets/{name}/uses`, which nodes use one), never a
value; no endpoint returns one. In the configured-token and key case the logging filter masks those two as well
([8.3](../08-cross-cutting-concepts/08.03-logging-observability.md)). The credential store itself, its limits and the
missing key rotation are in [8.6](../08-cross-cutting-concepts/08.06-credential-store.md).
