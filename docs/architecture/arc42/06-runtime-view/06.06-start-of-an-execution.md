## 6.6 Starting an execution

Every start of an artifact in a pipeline (the first one and every restart) goes through `RunEngine.start`
(`engine/runner.py`). It must hold for one artifact at a time, under concurrent requests, and it must leave the
database consistent if it fails half-way.

```
caller (route, /api/v1, MCP tool) → ArtifactService.start (resolves the target) → RunEngine.start

 1  in process, no await between check and add:
      task in _starting or _jobs              → 409 "already being processed"
      len(_starting) + len(_jobs) >= max_runs → 429 (OPENARTIFACT_MAX_CONCURRENT_RUNS)
      _starting.add(task)
 2  one transaction (_start):
      task missing → 404;  run row exists and is running → 409
      load the pipeline, build the snapshot, pick the start entry → TargetError / NestingError → 422
      claim (_claim), decided by the database:
         first run of the artifact:  INSERT ... ON CONFLICT (task_id) DO NOTHING
         a restart:                  UPDATE pipeline_runs SET status = running WHERE id = ? AND status != running
         rowcount != 1 → 409
      delete the run's stage rows (remembering which stages had passed), re-target the artifact,
      write the run row (status, started_by, snapshot, stage, action)
      open the execution (ExecutionHistory.open): next number from tasks.execution_seq, copies of the names,
         started_by, the snapshot as JSON
      one run_stages row per stage (passed / skipped before the start entry, pending from it on)
      prune the history of the artifact (retention, 6.9)
      COMMIT
 3  after the commit: publish run.updated, execution.updated / execution.deleted (and task.updated if the target changed),
      create the background task _execute, register it in _jobs; _starting.discard in a finally
```

Why two guards. The in-process set closes the window of step 1 and 2 (the request has not yet reached the database
row) and enforces the run cap; it is the reason a second request for the same artifact answers `409` without opening a
transaction. The conditional `INSERT`/`UPDATE` is what *decides* a race: SQLite serialises the writers, so exactly one
claim changes a row. Together with the unique run row per artifact (`task_id`) a double start is refused even if the
in-process check were bypassed. The cap and the sets are per process (single-process invariant, chapter 11).

Why the run and the execution are opened in one transaction. A crash or an error before the commit leaves neither a run
marked `running` without a task nor an execution without a run; the events go out only after the commit, so a browser
never sees a state that was rolled back (ADR-018).

The run row is reused by every start (it is the current state, `created_at` is reset); the execution row is new
(it is the history entry, with its own number). A `stop` pops the background task, cancels it, sets the run `stopped`
with the note "stopped" and closes the execution.
