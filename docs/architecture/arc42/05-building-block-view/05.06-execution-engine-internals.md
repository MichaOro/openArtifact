## 5.6 Execution engine internals

Package `openartifact/engine/` plus the credential modules (`credentials`). Decisions: ADR-021 (executors), ADR-023 (safety),
ADR-024 (credentials), ADR-025 (history), ADR-027 (flow replay). Sequences: [chapter 6](../06-runtime-view/README.md).

### Walk and the executor registry

`RunEngine` (`runner.py`) owns one `asyncio` task per active run (`_jobs`), capped by `max_concurrent_runs`. A start claims the run
row in one transaction (the database decides who is first: insert or conditional update, otherwise `409`), freezes the
pipeline and the definitions it uses into a **snapshot** (`snapshot.py`), opens an `Execution` (`history.open`), writes
the `RunStage` rows, applies retention and commits; only then the background task starts and the events are
published. The walk (`_walk`) follows the chain of the pipeline (`chain.py`): stage by stage, action by action along
*On Pass* / *On Error*; a `pipeline` node walks the called pipeline from the snapshot the same way. A run that takes
more than 1000 steps fails (a loop).

An action with a definition runs its graph from the trigger (`_run_action`). For every node on the way:

- `output` ends the action; the input reached (`pass` or `fail`) is the action's outcome;
- a kind with an **executor** (`executors.py`: `register_executor(kind, run, by_outcome=...)`) is run as
  `async (node, limits) -> NodeResult`; the node is left by *On Pass* or *On Fail* (`by_outcome=True`: Code, HTTP) or by
  the single *Next* output (timer);
- a kind without an executor passes through its `out` port;
- an action without a definition is an empty shell: it passes at once and leaves no step.

A dead end (an unconnected port) makes the action fail. Adding a node kind is a node type (`graph/node_types.py`)
plus an executor registration; the engine has no branch per kind.

`Limits` (from `Settings`) hands the executors their bounds: whether Code nodes are enabled, output limits, whether
HTTP may reach private networks, the Code resource limits and the secret resolver.

### Step recording

Every executed node becomes a `RunNodeResult` row in its own short transaction (`_record`): `seq` (per execution),
the position (`pipeline_id`, `depth`, `top_stage_id`, `stage_id`, `action_id`, `definition_id`, `node_id`), `kind`,
`outcome`, the port left by, and for Code and HTTP nodes exit code, output, reason and data. `executions.step_count` is
incremented and `run.updated` is published. Output is bounded twice: 256 K characters per node, and 1 M characters per
execution; beyond that the oldest outputs are replaced by a placeholder. A run read carries only the newest 200 steps with
output previews; `GET .../steps/{id}` and `.../results` have everything that was stored. Logs get id, kind and outcome only,
never the output. Steps carry no foreign keys into the snapshot; they are deleted with their execution.

### Run context

`engine/context.py` holds the context (`RunContext`: `vars`, `nodes`), the reference resolver (`RunView.render`, one
regular expression for `${secret:..}`, `${node...}` and `${var...}` so replaced values are never scanned again), the
node index of the frozen snapshot (`NodeIndex`: key to nodes; ambiguity is decided here) and the save-time hints
(`problems`). `_Walk` carries the context, loaded once from `executions.context` when the job starts. After an executor
returns, a passing node's `variables` are merged (a failure turns the result into a failed one) and `_record` adds the
node to the context and writes it with the step's single `UPDATE executions` (step count and context), in the same
transaction; no additional query. Executors get a `RunView` as third argument; the HTTP runner renders URL, header
values and body with it, the Code runner writes `context.json` (read-only) into its temporary directory. Caps: 4 KiB
output per node, 64 KiB context, 32 KiB variables (ADR-033).

### Branching nodes

`engine/branching.py` evaluates the If and Switch nodes: `compare` (the operators, strict number and boolean parsing,
`UnevaluableError` for operands that do not fit), `evaluate_if` and `evaluate_switch`, which resolve their texts through
`RunView.render` (secret references are never replaced there) and return a `NodeResult` whose new field `port` names the
output. The executors are registered with `by_outcome=False`; `_run_action` takes `result.port` before it falls back to
the port of the outcome, so Code, HTTP and the timer behave as before. The flow replay needs nothing new: it follows the
port recorded on each step (ADR-034).

### Code nodes

`code_runner.run_code` writes the code to a fresh directory (mode 0700) under the system temp directory and starts
`sh` or the application's own interpreter (`python -I`) as a child in its own process group. The environment is `PATH`, `LANG`, `HOME`,
the secrets the node names, and a marker `OPENARTIFACT_CODE_RUN`; no application setting. A small wrapper applies
`RLIMIT_CPU`, `RLIMIT_AS`, `RLIMIT_NPROC`, `RLIMIT_FSIZE`, `RLIMIT_NOFILE` and no core files, then replaces itself by the
script; if a limit cannot be applied the node fails. The result is "pass" on exit code 0; a JSON line in the output
(`ok`, `reason`, `data`) can refine it. On timeout the group gets `SIGTERM` and then `SIGKILL`; the same happens when
the run is stopped. `code_registry` records every started process (pid, start time, marker, directory) in a private
directory; at the next start `recover()` calls `cleanup_leftovers` and ends survivors of a hard-killed application.
Code nodes need an API token: in open mode (no token) they are refused unless `OPENARTIFACT_CODE_NODES_WITHOUT_TOKEN=true` is set for local development, and `OPENARTIFACT_CODE_NODES_ENABLED=false` forbids them altogether. The application is hardened against Code processes reading its own environment through `/proc` (`PR_SET_DUMPABLE=0`); this is not a sandbox: no network namespace, no file-system isolation, same user, limits per process not per cgroup.
Where `resource` or `/proc` is missing (non-Linux) the code runs unlimited and unrecorded, and the step says so. See
[8.1](../08-cross-cutting-concepts/08.01-security.md).

### HTTP nodes

`http_runner.run_http` sends one request with `httpx`: the URL's host is resolved here, every address is checked
(loopback, private, link-local and similar are refused unless `http_allow_private_networks`; unspecified, multicast and
metadata addresses always), and the connection goes to the checked address with the original `Host` header and TLS name
(no rebinding window). Redirects are not followed, environment proxies are ignored, the response is read up to a limit.
The node passes when the status matches `success_status` (default `200-299`).

### Credentials

A node holds `${secret:NAME}` (HTTP: URL path or query, headers, body; a reference before the path is refused) or, for Code,
a list of names. The executor (`_with_secrets`) asks `SecretStore.resolve` for the values, runs the node inside
`masked_in_logs`, and replaces every form of each value in the output, reason and data by `***` (`credentials.refs.mask_text`,
`mask_data`; as is, percent-encoded, Base64, JSON-escaped). A transformed value (hashed, split) is not found. Snapshots hold names
only. `credentials.crypto` encrypts with AES-256-GCM under an HKDF-SHA256 key derived from `OPENARTIFACT_SECRET_KEY`, a
random 96-bit nonce and the name as associated data; there is no key rotation. Saving needs an API token and an own
key (`409` otherwise), a value is at most 8 KiB, at most 32 secrets per node.

### History and retention

`ExecutionHistory` (`history.py`) opens and closes executions and applies retention; `RunEngine` calls it, and
`ArtifactService` for deletes. `close` mirrors the run's status, note, final stage and action and the
step count into the execution (`finished_at` is set on the first end). `prune` runs after a start, after an end and per artifact, newest number first: an execution is kept only if its rank is within the operator's guard
`execution_history_default_keep` (`0` = unlimited; there is no per-artifact policy, ADR-057; `apply_rules` adds the global retention rules
of ADR-052); a running execution is never deleted, and neither is the newest one. All mutations collect their
effects in `Changes`; the events `execution.updated` and `execution.deleted` are published after the commit. After
a restart, `recover()` marks running runs and orphaned running executions `stopped` with the note "interrupted".

### Flow replay

Only nodes of action definitions leave steps. `flow.build_flow` therefore replays the path from the frozen snapshot with
the engine's rules: start at the entry the execution began at, take On Pass or On Error by what the steps say, give each
run through an action definition the next group of steps (a group starts at a `trigger` step), and descend into called
pipelines. The result is a list of **visits** (one pass through a graph), the **traversed** edges and the **reached**
nodes per graph, with the graphs as frozen (`FlowGraph`, in the shape of the editor API). Snapshots written before the flow
existed lack ids, names, sizes and edge ids; they are completed on read. Nothing extra is recorded while a run runs, so
the replay and the engine can disagree only if their rules diverge (they share `chain.py`). The route is
`GET /api/tasks/{task}/executions/{id}/flow`.

### Global list

`history_query.list_executions` orders by `started_at` and `id` descending and pages with a keyset cursor `(started_at, id)`
(indexes of migration 0025), so rows that appear or vanish between requests neither repeat nor skip. Filters (status, origin,
pipeline id or name, free text or artifact number, time range) combine with AND; `summary` counts running, failed and done
in 24 hours and the total.
