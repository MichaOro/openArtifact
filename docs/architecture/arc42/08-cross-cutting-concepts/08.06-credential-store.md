## 8.6 Credential Store

Decision: [ADR-024](../../adr/024-credential-store.md). User-facing text: [credentials guide](../../../guides/credentials.md).
Runtime: [6.8](../06-runtime-view/06.08-credential-resolution.md).

**Purpose.** HTTP and Execute Command nodes need values that must not sit in a pipeline definition (an API key, a password).
A credential is a named value, stored encrypted; nodes refer to the name.

**Storage.** Table `secrets` (migration 0022): `id`, unique `name`, `value` (a blob), timestamps. Names match
`[A-Z][A-Z0-9_]{0,63}`; a value is non-empty, free of NUL, at most 8 KiB.

**Cryptography** (`credentials/crypto.py`):

| Item | Choice |
|------|--------|
| Cipher | AES-256-GCM (`cryptography` library) |
| Key | HKDF-SHA256 of `OPENARTIFACT_SECRET_KEY` with a fixed `info` of `openartifact/secret-store/v1`, no salt; the cookie signing uses the same setting through a different construction, so the two keys differ |
| Nonce | 96 bit, random per encryption |
| Associated data | the credential's name (a blob copied to another name fails to decrypt) |
| Format | one version byte `0x01`, then the nonce, then ciphertext and tag |
| Key length | the application refuses to start with a token and a secret key shorter than 32 characters |

**Access paths.**

- *Write and list:* `PUT/DELETE/GET /api/secrets`, `GET /api/secrets/{name}/uses`, the same under `/api/v1/secrets`, and the MCP
  tool `list_secrets` (names only). There is **no UI** yet; credentials are managed through the API.
- *Saving is allowed only with an API token and a secret key of the operator's own* (`SecretStore.writable`); otherwise `409`.
  Without a token the whole application is open and a stored credential would be usable, through any node, by everyone
  who can reach the port.
- *Reading values:* `SecretStore.resolve` is the only method that returns values, and only the executors call it. No
  endpoint, event, log line or step result carries a value; the API returns names and dates (`GET .../uses` lists nodes that
  refer to a name).
- *Use:* by name in a node (`${secret:NAME}` in an HTTP node's path, query, headers, body; a name list in an Execute Command node,
  at most 32), values injected at run time and masked afterwards.

**Limits, stated plainly.**

- **No key rotation.** A changed `OPENARTIFACT_SECRET_KEY` makes every stored credential unreadable (the node fails with
  "Secret NAME cannot be read: the secret key changed"); there is no re-encryption tool and no key versioning beyond the
  format byte. Changing the key also ends all browser sessions. A rotation concept is open (chapter 11).
- **The key and the database together reveal everything.** A backup of the database is safe without the key and fully
  readable with it. Keep the two apart.
- **Memory:** the derived key and the decrypted values of a running node are held in process memory while in use.
- **A node that receives a credential can leak it** deliberately in a form the masking does not recognise (hashed,
  split, reversed). Masking catches echoes and accidents. An Execute Command node receives credentials as environment variables.
- Credentials are only as protected from Execute Command nodes as the application's key is: the application is non-dumpable so
  `/proc/<ppid>/environ` is closed to a code process, and the database file is readable by it but holds only ciphertext
  ([8.5](08.05-execution-nodes-safety.md)).
- Deleting a credential that nodes still refer to is allowed; those nodes then fail at run time ("Secret NAME does not exist").
