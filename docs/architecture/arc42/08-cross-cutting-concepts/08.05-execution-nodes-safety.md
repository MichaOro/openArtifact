## 8.5 Execution Nodes and their Safety

Decision: [ADR-023](../../adr/023-safety-model-of-execution-nodes.md); executors: [ADR-021](../../adr/021-execution-nodes-as-executors.md).
User-facing text: [execution nodes guide](../../../guides/execution-nodes.md). Runtime: [6.7](../06-runtime-view/06.07-code-node-execution.md).

Two kinds of node reach outside the application: the **HTTP node** (a request to an address) and the **Code node** (a
script run as a child process). Both are registered executors (`engine/executors.py`); both take a node's settings from
the stored graph, so *whoever can edit a pipeline or action definition decides what runs*. With the single shared token
that is every token holder; in open mode (no token) it would be everyone with network access, which is why open mode
refuses Code nodes.

### What a Code node is

A Code node is remote code execution **by design**. The script runs as `sh` or the application's own Python (`-I`) in a
child process with the rights of the application's user. The protections below limit accidents and resource use; they
are not a sandbox, and the documentation must not suggest otherwise.

| Protection | Mechanism | Limit |
|------------|-----------|-------|
| Gate | `OPENARTIFACT_CODE_NODES_ENABLED` (default on); an API token is required, unless `OPENARTIFACT_CODE_NODES_WITHOUT_TOKEN=true` (local development; logs a warning) | One switch for the whole instance, no per-pipeline permission |
| Environment | built from scratch: `PATH`, `LANG`, `HOME` (the temp directory), the node's own credentials, a random marker; never an application setting | The code can read anything else the user can read |
| Parent's environment | the application sets `PR_SET_DUMPABLE=0`, so a same-user process cannot read `/proc/<ppid>/environ` (token, secret key), `mem` or `fd` of the application; the child itself is dumpable again after `exec` | Hardening against one attack, Linux only; the code can still read and write the database file |
| Time | timeout 1 to 600 s per node; SIGTERM, 2 s grace, SIGKILL for the whole process group; `RLIMIT_CPU` = timeout + 5 s | Wall-clock deadline per node only; there is none per run (chapter 11) |
| Memory | `RLIMIT_AS` (default 512 MiB, `OPENARTIFACT_CODE_MEMORY_LIMIT_MB`) | Address space, not resident memory; runtimes that reserve much (Java, Node, Go) need more; no cgroup |
| Processes | `RLIMIT_NPROC` = the user's current count + 64 (`OPENARTIFACT_CODE_PROCESS_LIMIT`); own session and process group; the whole group is killed at the end and on stop | Counted per user, not per tree; root is exempt (the image runs as UID 1000) |
| Files | `RLIMIT_FSIZE` (64 MiB), `RLIMIT_NOFILE` (256), no core files | Total disk or tmpfs use is not limited per node |
| Output | stdout and stderr each limited (`OPENARTIFACT_CODE_OUTPUT_LIMIT_BYTES`, 64 KiB), the tail is kept for the result protocol; a result is stored with at most 256 Ki characters, an execution with at most 1 Mi in total | Data larger than that is cut |
| A limit that cannot be applied | the wrapper exits 125 and the node **fails** instead of running unlimited | Where the `resource` module is missing (not Unix) the code runs unlimited and the reason says so |
| Orphans | `PR_SET_PDEATHSIG` kills the direct child with the application; a registry in `/tmp` lets the next start kill what the code left in the background (pid + start time, or the marker) | Linux with `/proc` only |
| Credentials | only the node's named secrets are passed; values and all their usual forms are masked in output, reason, data and logs | A node can leak a value in a form masking does not know |

**Not covered, whatever the limits** (stated in the code's docstring and kept here on purpose):

- **No network isolation.** A Code node reaches every address the application can, including cloud metadata
  services and internal hosts that the HTTP node refuses. The SSRF guard below does not apply to it. Egress rules belong
  to the host or the container network.
- **No file system isolation.** It reads and writes what the application's user can: `/data` and the database file in
  the container, everything the user owns on a bare-metal install. In the container the root file system is read-only,
  so only `/data` and `/tmp` are writable.
- **Same user, no privilege separation.** Running code processes under another user or in a container of their own is
  not implemented.
- **No cgroup**: memory and process limits are per process or per user, so a determined script can still use the
  container's memory in many small processes up to the container limit ([chapter 7](../07-deployment-view.md)).
- Code can call the application's own API from inside. With a token, it does not know it; in open mode with
  `CODE_NODES_WITHOUT_TOKEN`, it needs none.

### What an HTTP node is

An HTTP node sends one request (method, URL, headers, body from its settings; timeout 1 to 120 s) and passes if the
status is in the accepted set. The guard against server-side request forgery (`engine/http_runner.py`):

1. The application resolves the host name itself and checks **every** address; one refused address refuses the host.
2. Always refused: unspecified and multicast addresses and cloud metadata addresses (`169.254.169.254`, `169.254.170.2`,
   `100.100.100.200`, `fd00:ec2::254`); IPv4-mapped and NAT64 IPv6 forms are judged by the IPv4 address inside.
3. Refused unless `OPENARTIFACT_HTTP_ALLOW_PRIVATE_NETWORKS` is on: loopback, private, link-local, carrier-grade NAT
   and other non-public addresses (default off; self-hosters who call their own services switch it on).
4. The request goes to the *checked* address (the URL's host becomes the IP; `Host` and the TLS server name stay), so a
   name that resolves differently a moment later (DNS rebinding) cannot change the target.
5. Redirects are never followed (a 3xx is a status); proxies from the environment are ignored; the response is read only
   up to `OPENARTIFACT_HTTP_RESPONSE_LIMIT_BYTES` (1 MiB), uncompressed.
6. Credentials via `${secret:NAME}` only in the path, query, headers and body, never in scheme or host.

### Output as untrusted data

Step outputs are text from outside (a web response, a script's output). They are stored and shown as text (the UI
escapes them) and are never executed. For agents, the MCP tool descriptions tell the client not to treat results as
instructions; a client may ignore that, so an agent that reads step outputs should be run with that in mind
([security guide](../../../guides/security.md)).

The **tools of an Agent node** (ADR-040) apply the same rules: the MCP Client Tool's requests go through a transport
that vets and pins every address, the HTTP Request Tool through `guarded_exchange`, the Code Tool through `run_code` with
the Code node's switches. A tool's answer is foreign text for the model and the history; it is cut to 16 KiB, masked
for the run's secrets and never interpreted. Model values are inserted after the references are resolved and never
scanned again, and never into the scheme or host of a URL.

The **GitHub node and the Postgres node and tool** (ADR-041) follow the same pattern. The GitHub node uses `guarded_exchange`; the
values that become part of its address are validated and percent-encoded after the references, and its only write, a
comment, needs its own switch. The Postgres core connects to the vetted address (`hostaddr`), accepts a plain
connection URL only (no `options`, `service`, files or several hosts), binds every value as a parameter of the extended
protocol (which also allows one statement only) and runs the statement in a read-only transaction after a first query,
so the server refuses a change of the mode from inside the statement; writing is a switch of its own. The connection
URL is a secret: masked in results, details and logs, and absent from error texts.

### Honest summary

Switch on Code nodes only where everyone who may edit pipelines is trusted with the host account. The protections keep
mistakes and runaway scripts contained; they do not stop a script written to cause harm. A stronger setup would run
Code in a separate container or user with its own network policy; it is not built (chapter 11).
