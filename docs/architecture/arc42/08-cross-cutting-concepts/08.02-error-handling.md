## 8.2 Error Handling

### Response shapes

Every error answer from the API is JSON with one field, `detail`.

| Case | Status | Body |
|------|--------|------|
| A refusal by a service or the engine (`ArtifactError`) | its own `status` (404, 409, 413, 422, 429, ...) | `{"detail": "<message>"}` |
| Request validation (FastAPI/Pydantic) | 422 | `{"detail": [{"type", "loc", "msg", ...}, ...]}` a list; the rejected `input` and `ctx` are removed |
| Access, middleware and `HTTPException` | 400, 401, 403, 413, 415, 429, 503 | `{"detail": "<message>"}`; `401` carries `WWW-Authenticate: Bearer`; an HTML page request without access is redirected to `/login` instead |
| A bare `OpenArtifactError` | 400 | `{"detail": "<message>"}`, logged as a WARNING |
| `ConfigurationError` at run time | 503 | `{"detail": "<message>"}`, logged as an ERROR |
| Anything else | 500 | `{"detail": "Internal server error"}` (the message only with `OPENARTIFACT_DEBUG=true`), one ERROR line with exception class, method and path; uvicorn logs the traceback |

`detail` is a string except for `422` from validation. No answer carries a secret, a stack trace or (in production) an
exception message of an unexpected error. The OpenAPI document at `/api/docs` declares the error statuses a route can
produce ([API reference](../../../guides/api-reference.md)).

### Rules

- **One refusal: `ArtifactError`** (`exceptions.py`) has an HTTP `status` and a `message`. The services and the engine raise
  it; one application-level handler answers it. Routes do not translate errors, and there is no separate run error. The
  MCP server turns the same error into the tool's error text (`McpError`, so the agent sees the message), the integration
  API answers it like the browser API (ADR-018).
- The exception hierarchy has three classes: `OpenArtifactError` (base), `ArtifactError` (refusal) and
  `ConfigurationError` (invalid or missing configuration). Earlier unused error classes were removed
  ([ADR-032](../../adr/032-removal-of-the-unused-workspace-model.md)). A raw database error is not translated: it ends in
  the generic `500` handler.
- **Middleware refusals** (before the routes): `400` bad host, `413` too large, `403` cross-site, `415` wrong content type,
  `401` or a redirect to `/login` without access, `503` stream cap. The run cap `429` comes from the engine.
- **Persistence rule:** whoever changes data commits; a request session is not committed automatically, and a session
  closed without a commit discards its changes. An event is published only after the commit (ADR-018, [8.7](08.07-history-and-retention.md)).

### Specific cases

- **Secrets:** `409` when a credential is saved without an API token or without an own secret key; `422` for a name
  or value that breaks the rules (name pattern, empty value, NUL, more than 8 KiB); `404` when deleting an unknown name.
- **Executions:** `409` when deleting a running execution ("stop it first"); `422` for an unknown filter value in the global list or a
  malformed cursor.
- **Runs:** `409` for a second start, `429` at the run cap, `422` for a stage or action not in the pipeline. A missing
  connection, a nested pipeline that cannot go on, or more than 1000 steps ends the run as `failed` with a note; a stop keeps
  stage and action; a restart marks running runs `stopped` ("interrupted"). An unexpected exception in a run is logged with its
  traceback and ends the run `failed` with the note "Internal error".
- **A node that does not work is not an exception.** Executors return a `NodeResult` with outcome `pass` or `fail` and a
  `reason` ("Timeout after 30 s", "Exit code 2", "HTTP 500 is not an accepted status (200-299)", "Secret NAME does not
  exist"). The engine stores it as a step and leaves by the On Fail port; only a missing On Fail/On Error connection fails the
  run. A raised exception inside a node is caught and becomes `fail` with only the exception class name, because the
  text of an exception can hold a URL or an echoed secret ([6.8](../06-runtime-view/06.08-credential-resolution.md)).
- **Start:** a failed migration makes the entrypoint exit with status 1; an invalid security or settings configuration
  makes the application refuse to start; the output is in `docker compose logs`.
