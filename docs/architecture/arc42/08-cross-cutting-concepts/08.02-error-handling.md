## 8.2 Error Handling

- **One refusal: `ArtifactError`** (`exceptions.py`) has an HTTP `status` and a `message`. The services and the engine raise
  it; one application-level handler answers `{"detail": message}` with that status. Routes do not translate errors, and
  there is no separate run error. MCP turns the same error into the tool's error text (ADR-018).
- Other handlers: a bare `OpenArtifactError` is answered `400` and logged as a WARNING; `ConfigurationError` `503`; request
  validation `422` (the rejected input is not echoed); everything else `500` with the generic body `Internal server error`
  (the message only with `OPENARTIFACT_DEBUG=true`) and one ERROR log line naming exception class, method and path
  (uvicorn logs the traceback). Responses always have a `detail` field; no secrets in them or in logs.
- `PipelineError` and `DatabaseError` exist but nothing raises them (quarantined). A raw database error therefore ends in the
  `500` handler, not in a `503`.
- **Middleware refusals** (before the routes): `400` bad host, `413` too large, `403` cross-site, `415` wrong content type,
  `401` or a redirect to `/login` without access, `429` run cap, `503` stream cap.
- **Persistence rule:** whoever changes data commits; a request session is not committed automatically, and a session closed
  without a commit discards its changes (ADR-018).
- **Runs:** a missing connection, a nested pipeline that cannot go on, or more than 1000 steps ends the run as `failed` with
  a note; a stop keeps stage and action; a restart marks running runs `stopped` ("interrupted").
- **Start:** a failed migration makes the entrypoint exit with status 1; an invalid security configuration makes the
  application refuse to start; the migrations output is in `docker compose logs`.
