## 8.4 Board Concepts

- **One state owner:** the frontend `Board` holds all artifacts; REST responses, SSE events and
  optimistic changes all go through the idempotent `upsert`/`remove`, so order and duplicates do not matter.
- **Server is the authority:** optimistic changes are rolled back when the server refuses; events are
  published only after the commit.
- **Ordering:** fractional `position` per lane; a drop sends `before_id`, never an index.
- **Integrity:** `parent_id` is a real foreign key (`ON DELETE SET NULL`, enforced per connection); what SQL cannot express stays in the repository: parent cycles, detaching children with a resync, numbers from a counter table.
- **Design tokens:** colours, spacing, glass and lane hues are defined centrally in `tokens.css`; components never use raw values.
- **Accessibility (board):** semantic HTML, native `<dialog>`, keyboard alternatives for the board's pointer actions (Alt+arrows, Enter, Delete), live region announcements, `prefers-reduced-motion`. The graph editor's connections are pointer-only (chapter 11).
- **Wording:** the UI says "artifact"; code and API say `task` (see glossary).

## Update (2026-11-22): lanes are rows

Lanes are the rows of the table `lanes` (migration 0029; details and rules in [ADR-011](../../adr/011-board-interactions-sse-and-pointer-dnd.md)):
the owner adds lanes (at most 12), renames them (by clicking the name or through the lane's menu) and deletes them (only when empty, never
the last one). `tasks.status` is a foreign key to `lanes.key` with `ON DELETE RESTRICT`, so a lane with artifacts cannot disappear even when a
move and a delete race. The page renders the lanes on the server; `Board.setLanes` adds or removes lane sections from the server's own
template when `board.lanes` arrives (also from other tabs), so nothing needs a reload. The sidebar entry that was called Projects is called
**Board**.
