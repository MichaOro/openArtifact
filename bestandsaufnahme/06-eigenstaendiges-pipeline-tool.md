### Human command signals on a card (label-driven control)

- **Was sie tut:** The human steers only through labels on a forge issue; automation owns status and labels. ai:go = normal start (triage checks first); ai:ready = start the stored next_action (triage checks first, never for scheduler starts); ai:accept = human accepts a gate, stage_handover decides: mode 'ready' ends the stage without a run, mode 'run' sets next_action and starts; ai:slice = force (re)slicing into work packages; ai:force = skip triage; ai:pr-ready = gate passed, waits for the human to merge; human:review / human:question = hand-over (assignee to human, board status Ready/Waiting). Command labels are removed automatically right after execution, the event stays in the timeline. Writing pipeline start needs ai:ready AND the bot as assignee (order irrelevant) or ai:go; comments never start a run. Status labels: ai:queued, ai:processing, ai:failed, ai:implementation-ready, ai:autonomous, ai:gate-missing; type labels epic, work_package.
- **Auslöser und Eingaben:** Label/assignee events with sender identity (webhook); for writing: labeled/assigned events.
- **Ergebnis und Zustand:** issues.next_action, stages_done, timeline events.
- **Fehlerbehandlung:** Recent-command detection (20 min window via timeline events) read only the first 40 events until fixed on 2026-11-20; ai:accept/ai:slice are exempt from triage so a deliberate re-slice is not stopped.
- **Externe Systeme:** Forge issues (labels, assignee), project board status field.
- **Abstraktion für das Produkt:** Command channel on a card: a small fixed set of named human commands (start, force-start, accept-gate, re-slice, hand over, resume) reachable from UI, CLI, REST and MCP. A command is consumed once, appended to the card timeline and resolved by the pipeline definition into a transition; card status is system-owned, never hand-edited. Tier hint: MVP.
- **Beleg:** HO §3.2; AU §5.1 and App. A (labels); A4 §1, §5; NET-AG 'Status and labels belong to the automation'; UE 'Regeln des Nutzers'.

### Trigger intake: authenticity, idempotency and run origin

- **Was sie tut:** Forge webhook enters the orchestrator; HMAC signature verified (invalid -> 401, observations stored in webhook_signature_observation); 2xx must return within the forge 10 s limit. Duplicate events (labeled + assigned) produce one run through the unique issue key, ON CONFLICT ... WHERE state NOT IN (queued, processing), a 3 h busy check and SKIP LOCKED claiming; the delivery id is only recorded, never used for dedupe. Payload shape defines origin: webhook payload with action/sender = human start; scheduler payload with only issue/repository = autonomous start. Internal continuations (recovery, gatecheck, integrate) re-enter through authenticated internal webhooks (shared header token, body re-signed).
- **Fehlerbehandlung:** Documented weak points: delivery id not deduplicated; events endpoint has no authentication; shared re-entry token hard-coded in code nodes (rotation recommended); HMAC branch partly in observe mode and not live-tested (A1 §8, A4 §6).
- **Externe Systeme:** Forge webhooks; n8n webhook nodes.
- **Abstraktion für das Produkt:** Trigger service with mandatory authenticity check for external events, an idempotency key per delivery and an explicit origin (human | scheduler | system | internal) stored on every run and usable in rules (for example triage only for human origin). Internal continuations are in-process queue entries, not loopback webhooks. Tier hint: MVP (origin, idempotency); signatures with the first external adapter.
- **Beleg:** A4 §1, §6; HO §3.4(1), §4 principle 9; UE 'STAND 15.11.2026 spät' (triage applicable only if payload.sender present); AU §5.1.

### Structured human questions and hand-over to a human

- **Was sie tut:** Agents never ask interactively (started with --no-ask-user). A run that needs a decision ends with a question comment whose '### Rückfragen' block has per question: three plain-language context sentences (topic, situation, effect), one decision (max 25 words), 2-4 checkbox options (max 15 words each) with exactly one marked as recommendation plus an 'other, I comment' option; max 7 questions per round, gold first; evidence and ids below. Automation sets human:question, assigns the human, status Waiting. The human ticks boxes (phone friendly) and restarts; the agent reads its last question comment: a ticked box is the answer, later comments refine it, an unticked question stays open and is never decided by the agent. Hand-over also happens when a gate passes (ai:pr-ready) and when triage returns wait/none (human:review + assignee + status Ready). The health gate on 'pause' adds a ready-to-paste answer in the user's voice; resume after a pause needs a user comment, the answer is injected as its own prompt section and the health counter restarts (aiforge-resume-check).
- **Fehlerbehandlung:** Gate accepts final=question as a valid end; a comment alone never restarts a run (deliberate design decision, A4 §5).
- **Abstraktion für das Produkt:** Human decision request: a typed artifact on a card (questions, options, one recommended option, context, evidence) answerable from any device. Answers are structured, versioned and injected into the next run; unresolved questions stay open; the card moves to a Waiting state with an owner. Tier hint: MVP (ask/answer/resume), recommended (options, proposed answer).
- **Beleg:** NET-AG 'Questions to the author'; NET-RT rule 16; AU §5.7; HO §3.2, §3.5; NET/.github/ISSUE_TEMPLATE/outline-run.md step 8; A4 §5.

### Next-action resolution and persisted card state

- **Was sie tut:** Resolve Action picks the action in fixed order: (1) a recovery queue entry, (2) issues.next_action (written by the run-end decision, triage or accept), (3) the start action of the artefact type (smallest id in routing_rules; for epic: epic-gap-analysis). After each run 'Decide Next' applies the rules: next step, repeat with reason, hand-over or stage end. Per-issue state: state, current_action, lane, git_branch, parent_issue_number, use_case, next_action, stages_done, health_paused_at plus iteration counters; WPs additionally status (planned/building/drafted/created/failed), attempts, apply_json, implemented_at. An issue whose flags do not match reality would start with the wrong action (motivation for triage). The human never edits next_action by hand.
- **Ergebnis und Zustand:** issues(state, current_action, lane, git_branch, parent_issue_number, use_case, next_action, stages_done, health_paused_at), work_packages, wp_findings, wp_review_snapshots.

- **Abstraktion für das Produkt:** Explicit execution state on every card (current stage, next action, completed stages, lane, parent/child links, branch) owned by the engine and derived from definition plus results, with a documented resolution order, so a card can be restarted or healed at any stage. ### Bounded retry with reason, cycle counters and limits

- **Was sie tut:** A failed contract check or failed gate repeats the step with the failure reason injected into the prompt; max attempts per step; health checks at cycle 5 and every 5 (health_first_check, health_check_every). Other documented limits: gate re-runs max 2 per run window and integration attempts max 2 (writing), autonomous follow-up runs max 3 (autonomous_loop counter, reset after 6 h or a human start), recovery model switches max 10 per issue, same-launcher retry max 2, breather max 3. All thresholds are scheduler_setting rows (max_active_runs, health_*, ready_*, review_delta_mode, run_stall_minutes, implementation_ready_threshold).
- **Fehlerbehandlung:** Limits were sized for single-step runs (3 autonomous loops, 2 gate re-runs) and do not fit an 11-stage flow (A4 §4).
- **Abstraktion für das Produkt:** Bounded loops with feedback: the failure reason is a first-class input to the retry; limits exist per step, per run and per card, are configurable and visible; counters survive restarts. Tier hint: MVP.

### Two-layer verification after every agent step (contract validator + LLM goal gate)

- **Was sie tut:** After each agent step a machine contract check runs (marker, JSON schema, headings, readiness line equals JSON value, WP placeholders, size) and a second, different model (goal-gate, temperature 0.2; e.g. gates on DeepSeek while work runs on Qwen) judges the result against the agent's definition (role, task, prohibitions, contract) and returns criteria with evidence. A violation or gate fail repeats the step with the reason; verdicts are appended as collapsible blocks on the issue. Principle: the agent never asserts its own result.
- **Fehlerbehandlung:** The gate model (DeepSeek on the AI hub) occasionally breaks off; the pipeline absorbs it but it costs time (AU §6).
- **Abstraktion für das Produkt:** Per-step verification stack: deterministic validators first, then an LLM judge with its own model profile and criteria-with-evidence output; verdict stored on the card; failure feeds retry-with-reason. Tier hint: MVP (validators), recommended (LLM judge).
- **Beleg:** AU §2, §5.6, §5.7, §6; HO §3.4(6), §4 principle 2; MODEL §2.

### Result contract: typed result markers and script-posted results

- **Was sie tut:** The only valid run result is a comment by the bot identity whose first line is '<!-- aiforge:<action> -->' with machine-readable JSON. Markers in use: progress, report, question, answer, runlog, run, review, triage, epic-document, epic-merge-resolve, merge-needs-human. For implementation and merge a deterministic script posts the report (aiforge-impl-check --post, aiforge-merge-check --post) so the agent cannot merely assert success; without script success there is no valid result. The automation ignores marked comments (they never start runs) and tells agent from human comments only by the marker; per-run comments are folded into one run-log comment. Locally the same contract becomes a result file/event (expectFiles such as .aiforge/merge.md).

Tier hint: MVP.

### Health gate (loop governor)

- **Was sie tut:** After N cycles (first check at 5, then every 5) an agent (health-gate, temperature 0.2) assesses the loop history and returns continue / accept (goal practically reached -> close the stage via on_accept_action) / pause (question to the human). It detects diminishing returns and processing errors. On pause it supplies a ready-to-paste answer text; after the human answers (ai:ready or ai:accept) the counter restarts. Per-stage *-health rules exist (wp-implementation-health with on_accept 'implemented', epic-documentation-health, epic-merge-health). A human ai:accept is equivalent to a manual accept.
- **Fehlerbehandlung:** Health agent output also guards against agent processing errors; max cycles bound the loop.
- **Abstraktion für das Produkt:** Loop governor: a policy-driven checkpoint that decides continue / accept / pause from progress metrics plus an agent verdict; on pause it creates a decision request with a proposed answer; human accept closes the stage. Tier hint: recommended.
- **Beleg:** AU §5.7, §7.1(3); RRW; MS section 5; HO §3.4(7), §3.7 (health_paused_at).

### Rule-based readiness criteria and confirmation review

- **Was sie tut:** A WP is ready when no blocker and no critical/high finding is open and medium findings have been through at least one apply; alternatively a percent path (>=95). Before release a second, independent confirmation review runs; only without blocker and without critical/high is the WP released (label ai:implementation-ready). Switches: ready_rule_based, ready_rule_min_cycles=2, ready_confirm, implementation_ready_threshold=95.
- **Abstraktion für das Produkt:** Configurable exit criteria for refinement loops (severity thresholds, minimum cycles, score threshold) plus an independent confirmation pass before a card is marked ready. Tier hint: recommended.
- **Beleg:** AU §5.2, App. A (settings), App. B (wp-review-confirm).

### Findings ledger, delta review mode and binding user decisions

- **Was sie tut:** Every finding of every review is stored (severity, blocker flag, apply outcome, similarity to earlier findings = repeat detection) via record_review_findings / record_apply_outcomes / ledger_update, with snapshots in wp_review_snapshots. From the second review on, changes are reviewed completely while unchanged text only allows severe findings (review_delta_mode=1). User decisions written under '### Entscheidungen' are binding for review and apply and their implementation is checked deterministically.
- **Fehlerbehandlung:** Agents can still misread real text or quote old versions; gates, lint and manifest only catch part of it (AU §6).
- **Abstraktion für das Produkt:** Finding registry per card: typed findings with lifecycle (open -> fix claimed -> verified), repeat detection, delta-scoped reviews, and a 'decisions' section that binds later runs and is machine-checked. Tier hint: recommended.
- **Beleg:** AU §5.6, App. A (tables wp_findings, wp_review_snapshots, functions); HO §3.7.

### Per-run context pack and prompt placeholders

- **Was sie tut:** aiforge-wp-manifest builds a helper file per run with repository facts (files, identifiers with file:line), decisions and implementation status, finding history and changes since the last review; further scripts: collect-repo-context agent, epic-context, review-context. Prompts use placeholders ({{issue.url}}, {{issue.repo}}, {{issue.number}}, {{worktree}}, epic, WP position/skeleton/predecessors/overview, gate goal, health state). - **Fehlerbehandlung:** Appended-but-unversioned prompt paragraphs are a documented maintenance pain (AU §6).

### Outlining stage: model extracts facts, deterministic rules produce evidence-backed proposals

- **Was sie tut:** Implemented in NET (scripts/outline_stage.py + scripts/outlining/*, about 77 offline unit-test methods in 3 files, fake opencode, no network). Per scene one model call (extraction prompt versioned by sha256; headless run in an empty temp directory, no repo access) returns JSON events (kind, subject, action, verbatim quote max 100 chars, qty, holder). The engine validates deterministically (schema, beat address inside the scene, verbatim quote with folding of case/quote glyphs/umlaut spelling, state verbs required in the quote, unknown fields dropped) and rejects bad items with reasons. Rules R1-R12 are plain code: item used without introduction, item taken twice without stowing, light source used after extinguished/hidden, early time of day after noon, use after lost/broken, quantity change, opposite states in a scene, position jump, acting before learning, time-of-day order, forbidden/alias terms (terminology.json), cross-chapter terminology (R12). Each finding re-verifies its quotes. Artifact outline-proposal.v2 (JSON + Markdown) has status ok|partial|failed|aborted, coverage, extractor prompt hash, model expected vs verified (session export), rejected items, unsupported_classes (an explicit 'not checked' list) and open questions; exit codes 0/2/3/4/5/6; it never edits outlines, canon, memory or manuscript.
- **Ergebnis und Zustand:** Artifacts in .squad/workflow/outline-proposals/ (git-tracked by explicit path only).
- **Fehlerbehandlung:** Empty/invalid responses, timeouts, SIGTERM, manifest hash mismatch and source files changed during the run all yield a visible status and non-zero exit; likely_cause output_budget_exhausted is flagged when reasoning plus output tokens approach 4,096; a run is never reported as success unless status ok.
- **Abstraktion für das Produkt:** Evidence-first analysis action: the LLM only extracts structured facts with verbatim citations; the engine validates citations and applies deterministic rules; output is a proposal artifact with explicit coverage and a not-checked list, never a silent success; analysis actions are read-only by contract. Tier hint: optional as a domain plugin; the pattern is recommended.
- **Beleg:** NET-WIKI; NET/.squad/outlining/extract-prompt.md; NET/.github/skills/outline-propose/SKILL.md; NET/.squad/workflow/outline-proposals/ (artifacts incl. an ABORTED example); NET git log (feat/fix commits for failure diagnostics, partial scope, tiers).

### Outlining: continuity ledger, epochs/peers, finding tiers, accepted list and challenge

- **Was sie tut:** The ledger is the chapter-end state as structured data with verbatim evidence (items with state and quantity, characters with place/mood, knowledge, last time of day), built only from confirmed events. Entry state (--checks entry or --entry-state auto) feeds the predecessors' ledgers (same epoch from manifest 'timelines': past/present/forgotten) into the rules as pseudo events; the peers stage (R12) compares terminology with same-epoch chapters and optional peer_links; --update-ledger writes atomically only for status ok and complete coverage. Findings carry a tier: gold (strong evidence) or silver (plausible). An author-maintained accepted list with stable fingerprints suppresses decided findings (unmatched entries are reported). A challenge step asks a second model to classify each open finding (false_alarm, text_fix, canon_extension, author_decision) as an explicitly unverified judgement; canon extensions are only proposals to src/canon or the new-facts register. terms --suggest proposes terminology candidates from canon.
- **Fehlerbehandlung:** New event kinds (quantities, states, places with holder, knowledge) are only tested with prescribed events, not yet measured with a real model (NET-WIKI 'Bekannte Grenzen').
- **Abstraktion für das Produkt:** Cross-card continuity state (ledger) carried from predecessor to successor along configured sequences; finding tiers; author-owned suppression list keyed by stable fingerprints; optional second-opinion classification clearly marked unverified. Tier hint: optional.
- **Beleg:** NET-WIKI 'Kontinuität', 'Zeitlinien, Prüfstufen und Peers', 'Challenge'; NET/.squad/outlining/terminology.json.

### Quality contract and evidence rules (design)

- **Was sie tut:** Dimensions Q1 objects/resources, Q2 time, Q3 space/paths, Q4 causality/access, Q5 character knowledge, Q6 canon, Q7 uncertainty discipline, Q8 evidence, Q9 regression, Q10 consequence, plus L literary (neither compensating nor compensated); each dimension pass|fail|not-assessed, no aggregate score. Finding types contradiction (two sources or canon, two pieces of evidence), unexplained, assumption; severity blocker/major/minor/note; an open blocker fails the dimension; an 'unexplained' is never solved by the system but asked to the author. Evidence mandatory (file, address, verbatim quote max 200 chars) verified by script; findings without a valid quote are discarded and counted against the producing run; empty evidence lists are rejected. Auditor independence: other model/profile, own context without the coordinator's view, rules recomputed, blind sample of two scenes per sequence, no self-approval (role and model profile must differ). Gates G0 structure ... G6 author release; a change triggers an impact analysis and re-check of affected scenes plus neighbours.
- **Fehlerbehandlung:** FEAS found an auditor finding with an empty evidence list that a naive check would have passed (FEAS §2.4).
- **Abstraktion für das Produkt:** Quality gates with per-dimension verdicts and no averaged score, evidence-verified findings, severity-to-gate mapping, engine-enforced independent auditor, change-impact re-verification. Tier hint: optional pattern; evidence-verified findings recommended.
- **Beleg:** ARCH §F (F.1-F.5); FEAS §2.4, K7; A2 §6 (rule taxonomy).

### Issue memory: derived, hash-validated, single-writer (design + prototype)

- **Was sie tut:** Two levels: briefing.md (max 1,500 tokens, generated, valid_for manifest hash + memory_version) and modules (decisions.jsonl with verbatim author decisions and comment URL, findings.jsonl, facts/assumptions/questions, ledgers, deps.json, quality.json, changes.jsonl). Authoritative sources are issue comments (decisions), git history (changes) and content files; memory is a derived cache with source references and sha256 derived_from. Per-file hash comparison marks entries stale and triggers re-extraction. Agents never write memory; they propose a memory delta which an engine step validates (schema, source refs, quote exists verbatim) and applies with one writer and an optimistic memory_version check. Finding lifecycle open -> fix-claimed -> verified-fixed | reopened plus wontfix-by-author and question-pending. The prototype proved a ~300-token briefing for 8 findings + 1 decision, stale detection of exactly the changed file and session recovery from the briefing alone; write flow, commit and concurrency were not tested. Existing memory plugins were rejected (cloud, session-scoped, LLM-condensed, no hash validity).
- **Fehlerbehandlung:** Concurrent issues on the same chapter produce hash conflicts that must go to the author (ARCH E.4).
- **Abstraktion für das Produkt:** Per-card working memory: structured, versioned, source-referenced modules plus a generated briefing; authoritative human decisions kept verbatim; derived data invalidated automatically by content hashes; single engine-controlled writer. Tier hint: optional.
- **Beleg:** ARCH §E; FEAS §2.5; A3 §B (plugin survey).

### Detection-quality regression harness (frozen gold list and mutation tests)

- **Was sie tut:** The PoC package freezes a gold list (16 findings, 4 rule-detectable) and mutation sets (10 supported + 4 unsupported) with SHA-256 BEFORE the test and aborts evaluation if the rule file hash differs. Metrics: recall (>= 90 %, must-find set), noise share (<= 25 % target), evidence validity 100 %, mutation detection (>= 9/10), stability (3 runs, >= 80 % overlap), regression after a simulated fix. Results: gold 4/4 in all rounds; mutations 6/10 (round 1), 8/10 and 9/10 (round 2); Qwen 3 full runs: 70/72 valid scene responses, 789/790 quotes valid, Jaccard 0.40-0.56 (gold core stable), baseline precision 31-50 %. A runner/n8n self-test used a mock webhook and mock LLM (ok, timeout, 503 classified and attributed) and an enumeration of 1,024 cooling states checked independence.
- **Fehlerbehandlung:** Honest reporting rule: post-hoc rule changes are labelled Round 2 and regression tests built from known cases are flagged as not independent (NET-WIKI).
- **Abstraktion für das Produkt:** Pipeline self-test harness: frozen fixtures and mutation sets with hash-locked rules, repeatable metrics (recall, precision, evidence validity, stability), mock model/webhook doubles for failure classification, and replay of real runs as regression tests. Tier hint: recommended.
- **Beleg:** POC §1, §2, §3.2, §5, §6, §6b; POC2 README, frozen/, results/; FEAS §2.4; AU §6 and §7.4(3).

### Card timeline model with comments, events, labels and optimistic locking (web studio)

- **Was sie tut:** The journal studio of the target site is built like an issue tracker: an entry has a public number, labels, a version for optimistic locking (409 with the current state on conflict), comments (markdown, author_kind human|agent, optional machine marker such as aiforge:review, soft delete) and events (actor_kind human|agent|system, kind, jsonb data) written in the same transaction by diffing before/after. Labels such as ai:ready are meant to steer flows later; an agent API with a token is still missing (planned). Publishing is an explicit atomic action (blob write inside the DB transaction, rollback on failure) and published entries are locked; AI drafts are visible only after the owner publishes.
- **Fehlerbehandlung:** Changes made outside the studio only bump the version and create no events (VC-ADR ADR-44).
- **Abstraktion für das Produkt:** Card timeline: comments with author kind and marker, system events from before/after diffs in the same transaction, labels, optimistic locking, explicit publish/lock actions, agent API token. Tier hint: MVP (timeline + locking).
- **Beleg:** VC-STUDIO 'Datenmodell', 'Ausbau'; VC-ADR 11-studio.md ADR-42..44, ADR-46.

### Scheduled autonomous generation with guards and cron robustness

- **Was sie tut:** A nightly job writes at most one AI draft (DE+EN) per night until articlesPerWeek is reached and pauses while maxOpenDrafts await review; topic choice is deterministic scoring (community signals, coverage, interests) without AI; web material is treated as quoted data (prompt-injection protection, public http(s) targets only, links only to sources, no HTML); model list from DB config with fallback; rule-based quality score without a second model; drafts are labelled ki-entwurf and never published without the owner. The cron runner builds stable run keys per window (daily/weekly/biweekly/monthly/manual), a guard table with unique (job, run_key) for idempotency, an environment assertion before the run (names only, no values), logs skipped runs, detects missing runs by lookback, shows failed/missed runs as a banner in the studio, and offers a manual trigger with a bearer secret.
- **Fehlerbehandlung:** An outage since April stayed invisible for months because disabled cron calls wrote nothing; the fix was a skipped entry per call and missing-run detection (ADR-26).
- **Abstraktion für das Produkt:** Schedule-triggered pipelines: run keys and idempotency guard, enable flags in config, visibility of skipped/failed/missing runs, untrusted-input handling, quality scoring and a human release gate. Tier hint: recommended (scheduler), optional (journal use case).
- **Beleg:** VC-ADR 11-studio.md ADR-47; VC-ADR 08-cron-robustheit.md ADR-25..27; VC/docs/arc42/08-querschnittliche-konzepte/20-cron-system.md.

### Cost and budget guard with fail-closed generation

- **Was sie tut:** Per model run the USD cost is estimated and stored (worklab_generation_cost with per-model rates and fallback); a monthly budget guard warns at 80 % and marks exceeded at 100 %, after which generation is withheld (fail-closed); status per repo/component (ok|partial|withheld|failed|budget_exceeded) with consecutive failures; alerts for missed runs. Rule: if a step cannot finish safely it is withheld or blocked instead of publishing partial or unsafe output. On the pipeline side telemetry.usage records tokens/cost per request but there is no cost per issue or WP.
- **Fehlerbehandlung:** Budget exceeded -> summary withheld; failed repo isolated so others continue (isolate()).
- **Abstraktion für das Produkt:** Cost ledger per run/card with budgets, warn/exceed thresholds that withhold work, fail-closed behaviour and usage attribution to card/run/model. Tier hint: recommended.
- **Beleg:** VC/docs/arc42/08-querschnittliche-konzepte/18-fail-closed-health-und-ki-budget.md; AU §5.9, §6.

## Schmerzpunkte und Lehren

- SECRETS: several leaks (tokens printed in sessions, a token visible as a process argument, a hard-coded shared token in workflow code nodes, plaintext keys in local configs) forced rotation and a vault with no plaintext fallback; masking of outputs was explicitly demanded. Product: secrets provider, never in the agent environment, credential helpers for MCP/OTEL, masked logs. (HO §6-§7; SM; UE; A1 §7; A4 §6)
- A shared tmux/session server leaks environment variables into agent sessions; therefore no tokens in its environment, helper commands instead. (HO §7; UE 'Werkzeuge')
- Errors must never be swallowed: past hand-over errors vanished silently; the rule is decision log plus visible comment for every automatic decision. Counter-example still present: a DB trigger with EXCEPTION WHEN OTHERS THEN NULL. Note the intended fail-open of triage (run unchanged) must still be logged. (HO §7; MODEL L11)
- STATE VALIDATION: a WP with next_action set to an agent key (typo) failed three times with 'no active routing rule' while triage answered 'run unchanged' because that branch never looked at next_action; fix was a diagnose()/healer, plus a sweep that is still not scheduled. Lesson: validate card state against the pipeline definition before every start and cover scheduler/error paths too. (UE 20.11.)
- PAGINATION BUGS: the 'recent command' check read only the first 40 timeline events; agents read page 1 of 30 comments and concluded 'no new comments' (plugin now forces page size 100 and appends a hint); never hand a truncated tool result to a sub-agent. (UE 20.11.; NET-AG; POC2 plugin copy)
- FORGE API: GraphQL rate limit (5,000/h) became a problem -> REST only; mergeable is asynchronous and must be polled; Project v2 webhooks exist only for organisations. (HO §7; KO; A3 §D)
- n8n HAZARDS: a stale editor tab overwrites a workflow; drafts do not run until published; always check version history and note versionId for restore; plugin/prompt changes need a smoke run per model; core logic sits in two huge workflows (~230 nodes with embedded code). (KO 'Hinweis aus der Erfahrung'; UE; NET-RP last line; AU §6)
- OBSERVABILITY BLIND SPOT: successful n8n executions are not stored (saveDataSuccessExecution none), only errors visible; 10 sampled executions all 'error' within 0.04-9 s; real success rates only derivable from the DB (357 done / 53 failed in 7 days). (A4 §7)
- NO TESTS OF THE PIPELINE ITSELF: checks were manual against real data; owner's recommendation is to derive a test suite from real runs; the parallel-WP work is the first piece with real tests (branch naming, flag off, dependency validation, integration blocking, conflict abort). (AU §6, §7.4; TPW)
- HARD-WIRED TENANCY: user, bot account, project numbers, repos, paths, server are fixed; bot uses a personal token instead of a GitHub App; runs share host and filesystem without container or rights boundary. (AU §6)
- PROMPT MAINTENANCE: part of the instructions is appended by the workflow and is not in the versioned prompts; prompts, comments and UI are German only. (AU §6)
- MODEL INSTABILITY dominates failures: the AI-hub DeepSeek endpoint had 31 of 51 sessions failed and 30 recoveries; 504/503/litellm connection errors; failed runs lasted 209-239 minutes on average (max ~26 h); the gate model sometimes aborts. (MODEL §4.6, L15; A4 §7; AU §6)
- FREE-TIER QUOTAS: free providers have daily limits that the routing DB does not see (it reported 'free' while the limit was reached); OpenCode retries for hours without any signal unless a plugin aborts; counts are per source not per model; Gemini free quota was too small for agent runs; free models may vanish without notice. (POC §3.3; NET-RP; MODEL L4-L6; VC-RISK row 60)
- ROUTING GAPS: cooling-fallback starts even when everything is blocked; verify_score and max_parallel have no effect; quota logic hard-coded for one group; the error-attribution join inflates error counts by factor 6-16 (sessions share a copilot_session_id), test events (ABNAHMETEST, 60) pollute counters; recovery override not re-checked; Ollama outage has no fallback. (MODEL §8; POC §7)
- COMPLETION SIGNALLING: headless runs never emit agentStop, so the gate check would never fire; SIGTERM made the agent report idle which looked like 'finished' and triggered follow-up runs; the plugin therefore delays agentStop by 2.5 s and an external watcher reports process end. Lesson: define the completion contract (result file/event, exit code) instead of inferring it from agent idleness. (POC §4; POC2 plugin copy)
- TERMINAL DRIVING IS FRAGILE: prompts typed into a TUI, readiness by screen text, newlines stripped, Enter ignored for 30-50 s after the composer paints in a Claude Code version, trust-dialog layout reversed; status and pid of sessions lie. Prefer headless runners with file inputs/outputs; use sessions only for human visibility. (A1 §7; CODEMAN §0-§2)
- LONG MODEL RESPONSES TIME OUT and a failed run loses unsaved work: small steps, targeted edits, commit/push and a progress comment after each part, resume from the last progress comment and git log; a long script run (10-40 min) must be started in the background and polled because the agent bash tool aborts after 2 minutes. (NET-AG; NET/.github/ISSUE_TEMPLATE/outline-run.md step 4)
- LOOPS: agents repeat identical commands or 'no match' results; compaction loops at small context (70k); guards: 4th identical tool call within 10 minutes denied, third ignored denial aborts, breather after 10 compactions. (NET-AG; A4 §6; POC2 plugin copy)
- OUTPUT BUDGET: Qwen reasoning ate the 4,096 output budget (empty answer or silently thinner results); thinking could not be turned off through the hub; json_schema timed out while json_object worked; relative paths were hallucinated into wrong absolute paths; a missing stdin redirect hung a run. Lessons: detect finish_reason=length, per-role output budgets, absolute paths, timeout and </dev/null, result only from a file. (FEAS §2.1-§2.2, K1, K5, K6; POC §2)
- LLM JUDGE ALONE IS WEAK: found 1 of 4 expected issues; deterministic rules were the real detector; rules are coupled to the extractor's vocabulary (different action words caused false alarms); extractor invented states ('back in the backpack') and mislabelled mentions as 'lit'; baseline precision only 31-50 %; evidence checks must reject empty evidence lists; mutation test passed 6/10 then 8/10 and 9/10; run-to-run overlap only 0.40-0.56 on the full set (gold core stable). (FEAS §2.4; POC §2, §6, §6b)
- INDEPENDENCE OF AUDITOR is not guaranteed by infrastructure (56 of 1,024 cooling states collapse roles onto one model) and the first test used one model for both roles; enforce in the runner and log provenance. (POC §3.2; FEAS §2.4)
- IDEMPOTENCY IS WEAK: delivery id only observed; dedupe relies on unique keys, a 3 h busy check and SKIP LOCKED; one stale 'claimed' queue row with no kind existed; slot release after a crash without events depends on a 3 h timeout. (A4 §6; POC §7.1)
- LIMITS DESIGNED FOR ONE STEP: max 3 autonomous follow-ups, 2 gate re-runs and 2 integration attempts do not fit multi-stage flows; n8n has no multi-step-in-one-slot mechanism, hence the runner-script proposal. (A4 §4; FEAS §3, K4)
- LEGACY SPRAWL: many .bak-* scripts, three backup tables, routing_rules with many accreted columns, several n8n workflow generations active side by side, an old project poller still configured, documentation drifting from code (run-profiles.md vs actual cooling logic). Do not carry over. (HO §7; A1 §7; MODEL §8 L1-L3)
- EPICS AND LANES are partly mis-flagged in the board; cleanup was deferred as a separate topic after triage/merge. (HO §3.1, §7; KO 'SPÄTER')
- ENGINE FILES IN PRODUCT REPOS: pipeline reports (.aiforge/impl.md) were committed again and again and had to be removed from tracking several times; .aiforge/ and .tmp/ are git-ignored now. Engine artifacts belong outside the target repository. (VC git log --grep aiforge)
- SCOPE AND SIDE EFFECTS OF EPICS: an epic that forbids code changes still brought tests and a dependency bump; a merged PR made a page public against the epic definition; a dependency update created dozens of type errors in untouched files; other epics deleted tests; five epic PRs had to be merged by hand into a combined branch with docs conflicts and lockfile regeneration. This motivated the merge agent and the 'Offenes Delta' report; the product needs a scope guard and a delta report per card. (VC-RISK rows 70-75; VC git log)
- DISK/DB GROWTH: disk at 97 %, n8n DB 1.4 GB, agent DB 2.2 GB growing per run, docker logs, caches; needs retention policies and a cleanup timer. (SM)
- COST VISIBILITY: usage tables exist but there is no cost per issue/WP; usage rows join to sessions only partially (4,123 of 17,544 session-tagged rows). (AU §6; A5 §6)
- DOCS DERIVED FROM ARTIFACTS GO STALE: a handoff document carried an old manifest hash and contradicted the outline; register lines referenced beats that changed. Rule: derived documents carry the source hash and are checked against it. (A2 §4 Z9-Z10; NET-RT rule 12)
- MODEL/CLI POLICY: Qwen models reject an additional system block (local merge plugin needed); claude -p with a foreign model only after asking, otherwise Copilot CLI (subscription limits); free models have data_policy implications (author's hidden knowledge is loaded by runs); probes consume the same free quota as real runs. (HO §7; A3 §A6; NET-RP 'Datenschutz')
- ROLLOUT PATTERN THAT WORKED: additive migration with inactive rules, switch values 0/1/2, shadow mode compared with real issues, dry-run on real epics, backup + rollback statements, workflow restore points, per-issue escape label; still untested at hand-over time: the real user-start path and the full merge run. (KO; MS; UE)
- PARALLELISM NEEDS INTEGRATION SEMANTICS: 'created' is not 'integrated'; an unmerged parent must not release successors; a conflicting merge must leave the epic branch clean; slot reservations need expiry and an advisory lock; dependency graphs need cycle/missing-node validation. (PWP; PWP2; TPW)
- ONE HUMAN, MANY EPICS: the owner does not know which PR comes next and merges himself; the engine must tolerate arbitrary order by detecting conflicts at start and never auto-merging. (KO 'PRÄZISIERUNG'; HO §6)
- SECURITY POSTURE OF THE HOST (not product code but a deployment lesson): password SSH, no firewall, services bound on all interfaces, repeated failed logins from an internal host; default binds should be loopback. (SM)
