# 4. Parallele Work-Package-Ausführung

[Zurück zur Übersicht](../BESTANDSAUFNAHME.md)

*Gegenstand der Analyse:* Parallel work-package execution: epic slicing into WPs with dependencies, isolated worktrees/branches, shared concurrency cap, validation, sequential merge coordinator, recovery, cleanup, epic PR and merge-resolve gates. Sources: ~/docs/parallel-wp-*.md (5 files), ~/bin/aiforge-parallel-wp.py and the thin wrapper/helper scripts.

## Überblick

Status first: this is a built-but-not-live feature. The DB foundation and the Python scripts exist and pass 6 sandbox unit tests. The flag `parallel_wp_mode` is 0, Rule 26 is still `depends_mode=position-chain`, and the n8n Coding workflow patch is only a saved draft. The Events integration (validator and coordinator calls) is not implemented. The E2E audit (docs/parallel-wp-e2e-verification.md, 2026-11-19) rates it INCOMPLETE: no real parallel run ever happened. Everything below is therefore the designed functional model plus what the scripts actually do. Live production behaviour is still sequential. Source docs and scripts: ~/docs/parallel-wp-execution.md and the three deep-dive docs, ~/bin/aiforge-parallel-wp.py.

Intended lifecycle: (1) A planning agent cuts an epic into skeleton work packages. Each package has id, position, scope, acceptance items and a dependency list (`abhaengigkeiten`). Deterministic scripts check this (aiforge-wp-slicing, aiforge-wp-lint). (2) Packages are materialised as GitHub sub-issues (aiforge-wp) and as rows in work_packages. (3) The scheduler claims queue rows atomically (FOR UPDATE SKIP LOCKED plus deps_met). It reserves one of at most 2 OpenCode slots under a Postgres advisory lock. (4) A dedicated branch `epic/<N>-wp/<WP>` and a stable worktree per package are created from the epic branch. (5) The AI agent implements in that worktree. (6) A deterministic validator (impl-check against origin/epic/<N>) records the exact validated commit. (7) A per-epic merge coordinator merges validated packages in topological order with no-ff merges under a per-epic lock. It pushes the epic branch and marks the package `integrated`. Dependents unblock only on `integrated`. (8) When all packages are integrated, the existing epic stages run: epic-check, documentation, deterministic PR creation (aiforge-epic-pr), merge-resolve with a 5-check gate (aiforge-merge-check), and a human merge. (9) The sweeper removes worktrees and branches late and only when provably integrated.

Core design principles worth carrying over: agents never self-certify (every gate is a deterministic script); DB state is only advanced after Git proves it; every step is idempotent and resumable; feature-flagged additive rollout with legacy behaviour preserved; hard-to-undo steps happen last (the epic PR is merged by a human).

## Fähigkeiten

Verzeichnis: Epic slicing into work packages with dependency DAG; Two-level dependency model (stage gate plus same-epic WP graph); Atomic claim and shared concurrency cap (max 2 OpenCode sessions); Per-WP isolated branch and worktree provisioning; Deterministic WP validation gate recording the exact validated commit; Per-epic sequential merge coordinator (integration under lock); Interrupted-run, crash and divergence recovery matrix; Worktree and branch lifecycle sweeper; Work-package issue materialisation and linking (idempotent); WP refinement self-lint and run manifest (quality gates before implementation); Epic-level finalisation, PR creation and merge-resolve gate; Feature-flagged additive rollout with guarded activation and rollback

### Epic slicing into work packages with dependency DAG

- **Was sie tut:** An agent writes only a JSON slicing of the epic: summary, packages and changes. Each package has id, title, position, responsibility, goal, epic_bezug (epic requirement ids it covers), enthalten (what is included), nicht_enthalten (what is excluded), abhaengigkeiten (dependency ids), abnahme (acceptance items), atomaritaet and evidenz. aiforge-wp-slicing check validates it. It renders the comment and posts it, but only if the check passes. A patch mode (set/add/remove/new/remove-package operations, decimal positions renumbered to 1..n) refines an existing slicing. n8n then seeds work_packages from it.
- **Auslöser und Eingaben:** Triage routes the epic to the wp-slicing action (routing rules 6/7). Inputs are the epic body (requirement ids, out-of-scope ids) and the previous slicing comment (for patches).
- **Ergebnis und Zustand:** Slicing comment on the epic; work_packages rows (status planned, position, skeleton jsonb containing the dependencies).
- **Fehlerbehandlung:** Output lines FEHLER/HINWEIS then 'SLICING OK' or 'SLICING FEHLER (n)'; exit code 1 blocks posting, so the agent fixes it in the same run. Checks: duplicate ids; positions exactly 1..n; a dependency must exist and have a smaller position (so the graph is acyclic by construction at slicing time); epic_bezug must be non-empty and must reference known, non-out-of-scope ids; uncovered epic ids are an error; text and list size limits; hints against naming functions ('no how').
- **Externe Systeme:** GitHub issue comments (marker `<!-- aiforge:wp-slicing -->`, one JSON block), the aiforge-comment helper, the AI agent, n8n seeding work_packages.
- **Abstraktion für das Produkt:** Planning step that decomposes a parent card (epic) into child cards with an explicit dependency graph. Schema-validated output with a size budget per child. Each requirement of the parent must be covered by at least one child (coverage matrix computed, not claimed). Plan revision happens by patch operations with a change log. Posting is gated on validation.
- **Beleg:** bin/aiforge-wp-slicing (docstring, check_slicing, apply_patch, render); docs/parallel-wp-execution-architecture-assessment.md B.1; technical-deep-dive 2.3

### Two-level dependency model (stage gate plus same-epic WP graph)

- **Was sie tut:** Two separate mechanisms. (a) queue.depends_on holds cross-issue stage references such as {issue, stage}, evaluated by deps_met(queue_id) in the claim query. (b) skeleton.abhaengigkeiten holds the same-epic WP DAG, evaluated by wp_schedule, wp_check_deps and the new aiforge_wp_dep_ok. Routing Rule 26 `depends_mode` selects position-chain (the WP at position N waits for N-1, strictly sequential, current live setting) or skeleton (depend on all declared parents, enabling parallelism). wp_check_deps detects cycles, unknown references and blocked nodes. With the flag on, a dependent is runnable only when every direct parent has status created AND an integration row with status integrated (status created alone is explicitly not proof).
- **Auslöser und Eingaben:** enqueue_wp builds depends_on from depends_mode; the claim query calls deps_met; wp_start and wp_schedule decide what is runnable.
- **Ergebnis und Zustand:** queue.depends_on jsonb, work_packages.skeleton.abhaengigkeiten, aiforge_wp_integrations.status.
- **Fehlerbehandlung:** Phase-2 audit found that three more places treated 'created' as sufficient (DB: Load Work Package, wp_start, wp_schedule). Fix: helper aiforge_wp_dep_ok, tested in a rolled-back transaction. Premature epic completion risk: wp_schedule/wp_start could report 'done' while an accepted WP awaited integration. Fix: aiforge_wp_pending_integration blocks done. Open: backfill of integration rows for already finished epics (Epic 245: 8 WPs created, 0 integration rows). Open: enqueue_wp gates via depends_on (stage 'fertig' of parent), while the integrated proof applies only in deps_met/wp_schedule, so the two paths must be made consistent.
- **Externe Systeme:** PostgreSQL schema github_automation (work_packages, queue, routing_rules, aiforge_wp_integrations).
- **Abstraktion für das Produkt:** Per-pipeline dependency mode: strict chain by position or explicit DAG. Dependency satisfaction is defined as 'parent's result is merged into the integration branch', not 'parent's card is done'. Graph validation (cycle, missing node) before scheduling. Rule-level choice of dependency semantics.
- **Beleg:** docs/parallel-wp-execution.md (Lifecycle, Phase 2 audit); technical-deep-dive-parallel-wp-execution.md 2.3 and 5.x; assessment D.2 and E; aiforge-parallel-wp.py validate_graph/dependency_order/deps_integrated; e2e-verification 6 and 11

### Atomic claim and shared concurrency cap (max 2 OpenCode sessions)

- **Was sie tut:** Claim uses `FOR UPDATE SKIP LOCKED` with deps_met. Slot acquisition takes a Postgres advisory transaction lock ('aiforge-launcher-slot', then 'aiforge-opencode-global-slot') and writes a persistent short-lived reservation row (table opencode_slot_reservations, 15 min TTL, removed on terminal queue update). acquire_server_slot and acquire_launcher_slot both go through it for any launcher beginning with 'opencode'. Result is a hard global cap of 2 concurrent OpenCode runs; excess runs are parked as 'waiting' (busy / queued-ahead / global-cap). Claude launchers take an unlimited path. Slot acquisition happens BEFORE worktree creation. The cap is global (cross-epic and within-epic). Priority-aware 'ahead' counting avoids starvation. The older active_runs() excludes the target epic and counts only runs from the last 3 hours of activity. The newer reservation counts per queue row.
- **Auslöser und Eingaben:** Triggered by the n8n Coding and Writing workflows (nodes DB: Claim Queued Issue, DB: Acquire Server Slot, DB: Acquire Launcher Slot). Inputs: queue_id, launcher name, scheduler_setting max_active_runs=2.
- **Ergebnis und Zustand:** queue.status (pending, claimed, processing, waiting, done, failed), queue.launcher, opencode_slot_reservations rows.
- **Fehlerbehandlung:** Reservation TTL 15 min if the worker dies. Open finding F-2: acquire_launcher_slot ignores wp_id, so sibling WPs sharing (repo, issue) overwrite each other's launcher state. This only matters if the wp_schedule path (queue rows keyed on epic number + wp_id) is used. The live enqueue_wp path uses the WP's own issue number. F-1 (UNION de-duplication undercounts) was withdrawn after the operator clarified. OOM risk with 2 sessions (opencode_recycle_mb threshold, aiforge-opencode-recycle). Concurrency itself has never been tested at runtime (NOT TESTED).
- **Externe Systeme:** PostgreSQL only; the OpenCode server (launcher opencode-codeman and opencode-aiforge variants).
- **Abstraktion für das Produkt:** Scheduler with configurable global and per-resource-class concurrency limits (for example a limit per runner family), atomic reservation with expiry (lease) that survives worker crash, fairness/priority ordering, a 'waiting' state with reason, and an unlimited class for other runners.
- **Beleg:** docs/parallel-wp-execution.md (Locks, retries and recovery; Phase 2 findings 1); assessment D.1, D.4; technical-deep-dive 6.x; e2e-verification 10 and 14 (F-1 withdrawn, F-2)

### Per-WP isolated branch and worktree provisioning

- **Was sie tut:** aiforge-wp-worktree (wrapper for prepare_main in aiforge-parallel-wp.py) creates or reuses a dedicated branch `epic/<N>-wp/<WP_ID>` and the worktree `worktrees/<repo>/wp-<N>-<WP>`. It fetches the epic base first and fails if origin/epic/<N> is missing. It uses a host file lock (flock in .git/aiforge-locks) plus a DB advisory lock per repo:epic:wp. It rejects the call if another active queue run owns the same WP. States are created, reused, attached-existing (local branch) and attached-remote (from origin/<branch>). An existing branch is never reset. It symlinks node_modules, adds it to the git info/exclude, and records integration status 'working' with the head. Output is a single parseable line `AIFORGE wp-worktree {json}`. The feature flag must be on or nothing is changed.
- **Auslöser und Eingaben:** Coding workflow after slot acquisition: `aiforge-wp-worktree <repo> <epic> <wp_id> <queue_uuid>`.
- **Ergebnis und Zustand:** Branch, worktree dir, aiforge_wp_integrations row (working).
- **Fehlerbehandlung:** Refs `epic/245` and `epic/245/WP-1` cannot coexist in git (file vs directory ref), so the name `epic/<N>-wp/<WP>` was chosen after a real worktree test reproduced the collision. A branch registered to a missing worktree raises an error. A directory that exists but does not own the branch raises an error. Legacy (flag 0) behaviour before this: all WPs worked directly on the shared epic branch in per-run worktrees `issue-<N>-<queue8>`, which gave git race conditions under parallelism. The n8n Create Worktree step is currently shared-worktree and must be branched on the flag.
- **Externe Systeme:** git (worktrees), PostgreSQL, filesystem, remote origin.
- **Abstraktion für das Produkt:** Workspace isolation per card: each parallel work item gets its own branch and working directory derived from the integration branch, stable naming so a retry reattaches to the same workspace, never resets existing work, locked creation, one active run per card, machine-readable result.
- **Beleg:** bin/aiforge-parallel-wp.py prepare_worktree, prepare_main, git_lock; bin/aiforge-wp-worktree; docs/parallel-wp-execution.md (Git branch naming constraint, Locks); n8n nodes OpenCode: Worktree Plan, SSH: Create Worktree, Code: Check Worktree (draft version 2fa3bc8e only)

### Deterministic WP validation gate recording the exact validated commit

- **Was sie tut:** aiforge-wp-validate delegates to aiforge-impl-check with `--base-branch origin/epic/<N>`. It checks that the worktree sits on the expected WP branch and lies under the worktree root. impl-check performs 5 checks: run finished (commits, clean tree, pushed, .aiforge/impl.md), no new type errors vs a per-commit cached baseline, no test regression or new failure, build succeeds, and each test case TC-n has a matching passing test (or is named manual with a reason). On success it records the status 'validated' plus validated_head and fails if the branch moved during validation. On failure it records 'validation-failed' with the reasons (first 2000 chars). With the flag off or a non-WP branch it falls through to plain impl-check. Output is `AIFORGE wp-validation {json}`.
- **Auslöser und Eingaben:** Intended: between 'WP Gate Pass?' and 'Mark WP Created' in the Events workflow, or as rule 27 check_command. Inputs: repo, issue, worktree path.
- **Ergebnis und Zustand:** aiforge_wp_integrations(status validated or validation-failed, validated_head, last_error, attempts).
- **Fehlerbehandlung:** NOT wired: the Events workflow does not call the validator, and no routing_rules row references it. Unknown whether Events runs check_command/handover_command generically with the needed arguments (the scripts expect <repo> <wp_issue> <worktree>). The coordinator re-validates before merging and refuses if the WP head differs from validated_head ('WP branch changed after validation' -> recovery-required).
- **Externe Systeme:** aiforge-impl-check (astro check, vitest, npm build), git, PostgreSQL, optional GitHub comment via --post.
- **Abstraktion für das Produkt:** Verification gate per card, run by a deterministic tool (not the agent's own claim) against the integration branch as baseline. It pins the exact commit that passed. Any later change invalidates the proof. Results are structured and machine-readable, and a failing gate keeps the card out of the merge queue.
- **Beleg:** bin/aiforge-parallel-wp.py validate_wp, validator_main; bin/aiforge-wp-validate; assessment C.4; e2e-verification 4/14 (F-4: routing rule 27 still calls impl-check; validator not hooked in)

### Per-epic sequential merge coordinator (integration under lock)

- **Was sie tut:** aiforge-epic-merge-coordinator <repo> <epic> [--dry-run] runs merge_epic. It takes a Postgres session advisory lock per epic and a host file lock. It ensures a registered epic worktree and fetches origin/epic/<N>. If the epic worktree is dirty it refuses. It fast-forwards the local epic to the remote, or merges the remote if local commits all carry the [aiforge-wp:] marker. It refuses foreign local commits. It validates the whole dependency graph, orders candidates topologically (then by position), and for each WP: skips already-integrated WPs after verifying the integrated commit is an ancestor of the epic tip; waits if dependencies are not integrated; verifies branch tip equals validated_head; re-validates; sets status 'merging'; performs `git merge --no-ff` with message `Integrate <branch> (#issue) [aiforge-wp:<WP>]`; checks the post-merge worktree is clean with no MERGE_HEAD and no conflict markers; pushes `HEAD:refs/heads/epic/<N>`; records 'integrated' with integrated_head; and refreshes rows so dependents proceed in the same pass. On the first merge failure it stops the pass. Output is `AIFORGE epic-merge {json}`, exit 0 only if no merge-failed, validation-failed or recovery-required result. Dry-run is read-only and requires an existing epic worktree and a current origin ref.
- **Auslöser und Eingaben:** Planned: called after 'Mark WP Created' for the parent epic, and from the Coding Wake workflow as a recovery pass. Inputs: repo and epic number.
- **Ergebnis und Zustand:** aiforge_wp_integrations statuses: working, validated, merging, integrated, merge-failed, validation-failed, recovery-required (CHECK constraint, PK repo+epic+wp); merge commits on the epic branch carrying the marker.
- **Fehlerbehandlung:** Conflict: the merge is aborted, the epic tree is reset to its pre-merge HEAD, the row is stored as merge-failed and the pass stops. There is no automatic conflict resolution: a human resolves it, then reruns the coordinator. Interrupted MERGE_HEAD is aborted on restart and the rows in 'merging' become merge-failed. Merge committed locally but push or DB failed: the marker in the merge commit lets the retry verify the validated head is an ancestor, push, and repair the DB ('recovered-integrated'). Remote diverged: recovery-required. Branch missing, issue number missing or branch changed after validation: recovery-required. Documented rule: never mark integrated by hand without proving the tagged merge commit is an ancestor of the remote epic branch. The deep-dive risk list names WP branches going stale and suggests rebase inside the coordinator; the implemented coordinator uses merge only.
- **Externe Systeme:** git remote (push), PostgreSQL, filesystem worktrees.
- **Abstraktion für das Produkt:** Integration queue per parent card: serialised, dependency-ordered merging of validated child results into the parent's integration branch. One integrator at a time (lease or lock), fully idempotent and re-runnable, dry-run preview, structured per-item results (integrated, waiting, ready, recovery-required, merge-failed, validation-failed, already-integrated). Dependents are released only after their parent's merge is provably on the integration branch.
- **Beleg:** bin/aiforge-parallel-wp.py merge_epic, merge_branch, deps_integrated, integration_candidates; bin/aiforge-epic-merge-coordinator; docs/parallel-wp-execution.md (Locks, retries and recovery); technical-deep-dive 7.x

### Interrupted-run, crash and divergence recovery matrix

- **Was sie tut:** Documented 8 failure scenarios with detection, recovery and idempotence: (1) process died during implementation: no copilot_events heartbeat for 3 h -> queue failed plus recovery queue entry with the same wp_id; (2) died after commit: the coordinator finds the committed WP branch and tries integration; (3) died during merge: MERGE_HEAD -> merge --abort, requeue; (4) validation failure: exit code != 0 -> retry up to max_attempts, then triage comments to the user; (5) DB and Git diverge: sweep plus triage reconcile; (6) OpenCode session unreachable: HTTP check on port 4096 plus cgroup memory check -> aiforge-opencode-recycle restarts the service when idle and high memory; (7) worktree present but queue done: sweeper removes after a 30 min grace; (8) queue active but worktree gone: queue failed plus recovery entry. A parallel-aware recovery idea: if a WP fails, dependents revert to planned and are re-queued, with a logged cascade.
- **Auslöser und Eingaben:** aiforge-triage (heartbeat), n8n wake workflow, sweep at run end, recycle service.
- **Ergebnis und Zustand:** queue failed plus recovery entries; sessions status; integration statuses.
- **Fehlerbehandlung:** Most scenarios are documented design, and the e2e audit marks nearly all live recovery tests NOT TESTED. The parallel-aware cascade re-queue appears only in the assessment as a proposal. Note the idempotence table itself flags worktree creation and session register as not idempotent (existence checks guard them).
- **Externe Systeme:** PostgreSQL (queue, sessions, copilot_events), OpenCode HTTP, systemd.
- **Abstraktion für das Produkt:** Reconciler or watchdog that continuously compares queue state, session heartbeat, workspace existence and git state, and repairs or escalates. Retry policy with a max-attempts cap and an escalation to a human comment. Recovery entries tied to the same logical work item. Cascade re-queue of dependents.
- **Beleg:** docs/parallel-wp-execution-technical-deep-dive.md section 8.1/8.2; assessment F.3/F.4; e2e-verification 13

### Worktree and branch lifecycle sweeper

- **Was sie tut:** aiforge-worktree-sweep [--dry-run] is called by n8n at every run end (event-driven, never timer). It deletes only pipeline-created directories (issue-<nr>-<queue8>, wp-<epic>-<WP>, impl-base-*). Kept if: it is the workdir of an active session; its queue id is claimed/processing; modified in the last 30 min; or, for WP worktrees, the integration row is not 'integrated' or integrated less than 7 days ago. After 30 days AND when the branch is an ancestor of origin/epic/<N> AND no active queue run exists, it deletes the local branch (`branch -d`). It removes run temp files (<dir>.*.md/.json) and stale /tmp/aiforge-run.* dirs older than 6 h, and runs worktree prune. If the DB is unreachable it keeps everything and prints a skipped line. It never fails (exit 0) and prints `AIFORGE sweep removed= kept= freed_mb=`.
- **Auslöser und Eingaben:** n8n GitHub.Agentic.Events node 'Code: Cleanup Command' after a run's own worktree was removed.
- **Ergebnis und Zustand:** Freed disk, pruned refs; one printed line per action.
- **Fehlerbehandlung:** Never touches manual worktrees or patches/. Unintegrated WP worktrees are protected indefinitely (potential disk growth, unknown policy for abandoned WPs: inferred, not stated).
- **Externe Systeme:** git, filesystem, PostgreSQL via psql.
- **Abstraktion für das Produkt:** Retention policy for per-item workspaces: protect anything unintegrated or in recovery, grace periods before deletion, deletion conditional on proof the work is contained in the integration branch, event-driven cleanup, dry-run, safe-by-default when state is unavailable.
- **Beleg:** bin/aiforge-worktree-sweep; docs/parallel-wp-execution.md (Components); deep-dive scenario 7

### Work-package issue materialisation and linking (idempotent)

- **Was sie tut:** aiforge-wp create/update/relink/render creates a package as a GitHub issue under the bot identity with labels but no assignee (the pipeline only starts with the label ai:ready plus the agent assignment). It links it as a sub-issue of the epic. Idempotent: it looks up an existing issue by the metadata block `<!-- aiforge:wp {id, epic} -->` across open and closed `work_package` issues and does not duplicate. Placeholders [[WP-x]] are replaced by #number via a map, and `relink` rewrites placeholders in all issues. Deterministic REST, no LLM; the token is never printed.
- **Auslöser und Eingaben:** Called after slicing/building with body file, epic number and map.json.
- **Ergebnis und Zustand:** JSON {number,id,url,existing}; GitHub issues.
- **Fehlerbehandlung:** A missing or mismatching metadata block fails fast; a repeat after a partial failure re-links without a duplicate (link errors ignored if already linked); pagination scan capped at 10 pages of 100.
- **Externe Systeme:** GitHub REST (issues, sub_issues) via gh CLI as the bot account.
- **Abstraktion für das Produkt:** Child-card creation API: idempotent by stable external key, parent linkage, symbolic cross-references resolved after ids are known, bulk relink, dry-run.
- **Beleg:** bin/aiforge-wp (docstring, find_existing, apply_map)

### WP refinement self-lint and run manifest (quality gates before implementation)

- **Was sie tut:** Before implementation, a package passes wp-review -> wp-apply loops. aiforge-wp-lint (run by the agent itself, mirroring the Events contract check) validates review comments: marker first line; readiness percent equals JSON and band (95-100 ready, 80-94 conditional, <80 not_ready); exactly one JSON block; finding fields and enums (category, severity, confidence, implementationBlocker); same finding ids in text and JSON; required sections; not a near-duplicate of the previous review; no CJK characters in German text. For apply results it checks .aiforge/wp.md headings and order, acceptance criteria, one changeLog entry per finding, and that user decisions are preserved. aiforge-wp-manifest builds a temporary facts file for the run: paths and identifiers named in the package text checked against the repo (exists, lines, git grep hits, new vs wrong names), the finding history with apply outcomes, the diff since the last reviewed text, and the user decisions with their implementation status.
- **Auslöser und Eingaben:** wp-review, wp-review-confirm, wp-apply actions; manifest generated by Coding workflow 'Code: Run Files Command -> SSH: Write Run Prompts'.
- **Ergebnis und Zustand:** Review comments with markers; wp_findings; snapshots; temporary manifest.md kept under the git-excluded .aiforge/ dir.
- **Fehlerbehandlung:** Lint output FEHLER/HINWEIS plus LINT OK/FEHLER with exit codes. Manifest errors never stop the run; a section that cannot be built says so. Documented slip: a model wrote Chinese characters into German WP text and failed the gate (hence the CJK check).
- **Externe Systeme:** GitHub comments via aiforge-comment, git, PostgreSQL (wp_findings, wp_review_snapshots, scheduler_setting review_delta_mode).
- **Abstraktion für das Produkt:** Pre-execution readiness gate on each card: structured review with a scored readiness band, apply/confirm loop, fact-checking of references against the real workspace, history/delta context for the reviewer, agent-side self-lint so contract errors are fixed within the run rather than costing a cycle.
- **Beleg:** bin/aiforge-wp-lint (header and lint_review); bin/aiforge-wp-manifest (header); assessment B.1 and B.2 (rules 8-12, 19)

### Epic-level finalisation, PR creation and merge-resolve gate

- **Was sie tut:** After all packages are integrated: epic-finalisation (aiforge-epic-check), epic-documentation (documenter writes a comment `<!-- aiforge:epic-document -->` with a '## PR-Text' section of Title and Description), and the hand-over command aiforge-epic-pr. aiforge-epic-pr takes the newest such comment, creates the PR epic/<N> -> default branch, appends 'Closes #N' and an origin line, assigns and requests review from the owner, and never merges. It is idempotent (an existing open PR is reported, not overwritten). It requires the branch to exist and be ahead of base. It comments the result on the epic and always exits 0 so the hand-over never blocks. Then epic-merge-resolve: an agent merges the default branch into the epic branch, and aiforge-merge-check verifies 5 things before posting the result marker `<!-- aiforge:epic-merge-resolve -->`: no open merge; origin/<default> is contained; no conflict markers; clean tree and HEAD == origin branch (pushed); PR mergeable per the GitHub API (polls up to 60 s). If the agent aborts (report .aiforge/merge.md, base not contained, no open merge) the script exits 3 and posts a needs-human comment `<!-- aiforge:merge-needs-human -->` mentioning the owner. A human merges the PR.
- **Auslöser und Eingaben:** Routing handover_command after the passed epic-document-gate; merge-check as check_command of epic-merge-resolve. Inputs: repo, epic, worktree.
- **Ergebnis und Zustand:** Result lines 'AIFORGE epic-pr ok|exists|failed' and 'AIFORGE merge-check {json}'; epic comments with markers; the PR.
- **Fehlerbehandlung:** Failures are reported as comments ('PR nicht angelegt' with the reason) so the PR can be created manually. Exit codes: merge-check 0 ok, 1 defects, 2 usage, 3 agent abort.
- **Externe Systeme:** GitHub REST (pulls, compare, comments, requested reviewers) as the bot account, git, aiforge-comment.
- **Abstraktion für das Produkt:** Delivery stage per parent card: generated change description, idempotent PR creation, a final 'mergeable' gate with explicit human-escalation path, human approval before the final merge. Agent claims are verified by deterministic checks, and abort leads to escalation instead of a fake pass.
- **Beleg:** bin/aiforge-epic-pr (docstring); bin/aiforge-merge-check (docstring, main); assessment B.1/F.1; e2e-verification 14 F-4 (stage epic-merge rules 40-42 is the PR step, not the WP merge, do not confuse)

### Feature-flagged additive rollout with guarded activation and rollback

- **Was sie tut:** parallel_wp_mode lives in scheduler_setting (0 = legacy). The SQL migration is additive. Legacy slot functions keep legacy behaviour at flag 0. sql/enable-parallel-wp.sql is a guarded rollout operation: it verifies Rule 26 and only then sets depends_mode='skeleton' and flag 1. All scripts refuse to act when the flag is off, except validate which falls back to impl-check. An 8-step rollout procedure is documented: verify flag 0, import the workflow changes, choose a test epic with 2 independent plus 1 dependent WP, check isolation, check the slot cap with a third launcher family parked, validate and merge with the dependent blocked until the parent is merged, exercise 5 failure cases (conflict, interrupted merge, merge-ok/DB-fail, missing worktree, remote advanced), then enable. Backups of the n8n workflows (86/154/61 nodes) and rollback SQL for the redefined functions are kept; n8n version restore is possible.
- **Auslöser und Eingaben:** Operator-run SQL and workflow import.

## Schmerzpunkte und Lehren

- Branch-name collision: git cannot hold refs `epic/245` and `epic/245/WP-1` at once (ref file vs directory). Confirmed by a real worktree test. The product must pick a non-nested naming scheme (`epic/<N>-wp/<WP>`) for child branches. (docs/parallel-wp-execution.md)
- Original design had NO per-WP branches: branch_mode=epic-branch meant all WPs committed directly on epic/<N> in per-run worktrees, so true parallelism would cause same-branch git races. The serialisation came from n8n claim timing and triage routing, not from a DB guard. The product needs workspace isolation per card as a first-class concept. (assessment A)
- The early analyses were wrong twice: Evaluation 004 claimed the dependency checks were unused, but deps_met() was in the claim query. Later F-1 (slot undercounting by WP) was withdrawn once enqueue_wp was seen to use the WP's own issue number. Lesson: verify scheduler behaviour against live function source and rows, not documents. (technical-deep-dive 'Kritische Korrektur'; e2e-verification 14)
- 'created' status is not proof of integration. Four places (aiforge_queue_deps_met, DB: Load Work Package, wp_start, wp_schedule) treated it as sufficient. Also, 'done' could be reported while an accepted WP still awaited integration, which would close and hand over the epic before the merge. The product must define dependency satisfaction as 'merged and verified on the integration branch' and block epic completion while integrations are pending.
- Two disconnected state systems: DB status and Git reality can diverge (merge commit made but DB not updated, or the reverse). The solution is a marker in the merge commit message ([aiforge-wp:<id>]) plus ancestor checks to repair state. Never set 'integrated' by hand. The product needs an idempotent reconcile between its own state and the repository.
- Workflow wiring gap: scripts and DB layer exist but the Events workflow does not call validator or coordinator, and routing rules 27/36/28 still use impl-check or have no hand-over. It is unknown whether check_command/handover_command are executed generically with the needed arguments. Lesson: the pipeline's step hooks (check command, hand-over command with per-stage arguments) must be a generic, documented extension point, not hard-coded n8n nodes.
- Existing finished epics have no integration rows (Epic 245: 8 created WPs, 0 rows), so enabling the flag would regard them as unintegrated. Any new gate semantics needs a backfill or exclusion strategy.
- Slot accounting is easy to get wrong: active_runs() excludes the target epic and counts only the last 3 h of activity; acquire_launcher_slot ignores wp_id and overwrites sibling runs' launcher; slot function was originally called after worktree creation in the n8n Coding workflow (now before, per the audit). Locks need leases (15 min TTL) so crashed workers do not leak slots.
- Retry storms are costly: WP-6 of epic 255 was retried ~15 times (2-20 min each, about 4 h) before the epic was marked failed. Sequential position-chain compounds a failing WP. Motivates a max-attempts cap, cascade re-queue of dependents and early escalation to a human.
- Merge conflicts have no automatic resolution in the WP merge path: conflict means abort, status merge-failed, and the coordinator stops its pass. Risk of stale WP branches during long runs was noted (suggested rebase, not implemented). Possible mitigation proposed: file-scope declarations in skeleton 'enthalten' to detect overlapping packages and force them sequential (proposal only).
- Resource limits: OpenCode runs out of memory with 3 GB+ and has a hard 2-session cap; a recycle service restarts an idle, high-memory server. The product needs a resource-aware concurrency limit and a recovery service for runner processes.
- Models make contract slips (Chinese characters in German text, stale or duplicate review comments, wrong JSON enums). The answer was an agent-side lint that mirrors the pipeline's gate so errors are fixed within the run. Add 'pre-submit self-check' as a product pattern.
- Agents' own claims are never trusted: impl-check, wp-slicing check, merge-check and epic-pr are deterministic scripts with structured last-line results ('AIFORGE ... {json}') and exit codes. Hand-over steps (epic-pr) never fail the pipeline and report by comment instead.
- Hand-over and test constraints: no real parallel run has ever happened. Testing in production was blocked because creating an epic could trigger the live pipeline. A sandbox project with isolated triggers is a prerequisite for validating scheduler changes.
- Documentation drift: docs/parallel-wp-execution.md still states WP-7 #256 is processing although the audit found it done; the active workflow version pointer was never independently verified. Keep the status in the system, not in prose.
