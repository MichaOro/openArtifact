# 8. GitHub-Projekt-Integration und Telemetrie (Grafana)

*Gegenstand der Analyse:* A) GitHub Project / forge integration of the owner's AI pipeline (gen-1 board poller config + state, gh CLI usage in ~/bin, project model: statuses, fields, labels, issue/PR lifecycle, comments contract, how board state drives automation) and B) telemetry stack (~/repos/telemetry: README, Control Center doc, ai-usage + ai-pipeline-control-center + server-load Grafana dashboards parsed panel by panel, db/migrations, OTel collector, SHADOW_*/REPAIR reports) with derived observability requirements. ## Überblick

TWO GENERATIONS OF GITHUB INTEGRATION. Gen-1 (2026-10-25/26; ~/bin/github-project-ai + ~/.config/github-project-ai/config.toml) is a 60 s poller on a personal Projects v2 board that starts an isolated Copilot job when a card ENTERS status 'Ready for AI'. It logged about 1,240 lines (1,219 polls), queued 2 jobs (one 'needs_human_clarification', one 'success without a commit' x3), completed 0, and was left behind (timer not enabled, superseded). Gen-2 ('aiForge', since 2026-11-01; ~/bin/aiforge-*, n8n workflows, PostgreSQL schema github_automation) uses GitHub ISSUES as the UI: a run starts when an issue has label ai:ready AND is assigned to a bot account; labels + assignee swap + board Status say who holds the ball and why; agents answer only with marker comments whose first line is <!-- aiforge:<action> --> followed by a JSON block that a contract validator checks BEFORE posting; all orchestration state (stage, next_action, queue, sessions, work packages, triage decisions) lives in PostgreSQL, and the board is reduced to Status (Ready / In progress / Done), 'Run Profile' (model cluster) and 'Läufe' (run counter). GitHub access is gh CLI: REST under a bot token for labels/comments/PRs/sub-issues (to avoid the 5,000/h GraphQL budget) and Projects v2 GraphQL under the human login (bot token has no project scope).

PROJECT MODEL. Boards: Project 5 'netrats' (gen-1 config, writing pipeline, field Läufe; Status options Backlog / Ready for AI / In progress / In review / Done; writing scripts use Backlog / In Progress / Waiting / Done, runs use Queued) and Project 7 'agentic.Coding' (default of aiforge-project; Status Ready / In progress / Done). Fields: Status, Run Profile, Läufe (+ legacy Stage, Stream, Action, State, Lane, Artefakt type, Strategy, Prompt key, Git Branch, Iteration, Next Action now in the DB). Labels: starts ai:ready + bot assignee, ai:go; commands ai:slice, ai:accept, ai:force; states ai:queued, ai:processing, ai:failed, ai:autonomous, ai:gate-missing, ai:implementation-ready, ai:implemented; hand-over human:review, human:question, ai:pr-ready; types epic, work_package.

LIFECYCLE (coding). Epic issue (label epic) -> refinement loops -> slicing into work-package sub-issues (label work_package, no auto-start) -> build/review/apply loops with goal gates, health watchdog and confirmation review -> ai:implementation-ready -> implementation on epic/<N>-wp/<WP> branches verified by deterministic scripts (agent never self-asserts) -> epic finalise (tests, measurable criteria, delta list) -> epic document (PR text) -> script opens PR epic/<N> -> default branch (assignee + reviewer = human, 'Closes #N') -> optional conflict-resolution run -> HUMAN merges (never automated) -> epic closes; board Done strips all labels and assignees. Writing use case: run on ai/issue-<n> worktree, final report / question / answer comments, human answers by ticking checkboxes. Scale on 2026-11-19: 18 epics, 91 work packages (84 implemented), 2,777 sessions, 26,132 events, 28,533 tool calls, 31 routing rules.

TELEMETRY. Five sources (OpenRouter OTLP broadcast, LiteLLM OTel spans, Claude Code OTel logs, OpenCode local SQLite via adapter, AI Hub GraphQL import) are normalised into telemetry.usage (~110k rows on 2026-09-23) with two cost notions: actual_cost (billed) and shadow_cost (notional list-price estimate with provenance + resolution status), a canonical price book with validity windows, and an alias/entity resolver with async discovery. Grafana (provisioned from files, read-only DB role, raw SQL) has three dashboards: ai-usage (24 panels, no rows; filters source/provider/model/shadow_source; quota rings), ai-pipeline-control-center (v32: 25 content panels in rows A-D; filters repository/use_case; reads github_automation.*; only 2 panels touch telemetry.usage and those are NOT attributable to issues/runs) and server-load (5 panels from host_sample). No alert rules exist.

OBSERVABILITY REQUIREMENTS (synthesis; detail in capability B22): the new product needs (1) a usage ledger row per model call with native attribution to card / pipeline run / stage / action / agent / model cluster, (2) dual cost accounting (billed vs notional) with provenance and a versioned price book, (3) a run/session/queue/event ledger with an explicit state machine, (4) views: usage KPIs and breakdowns, quota/budget meters, cost per card/stage, pipeline snapshot incl. waiting-for-human by reason, reliability KPIs, durations, failure taxonomy, model health, capacity vs concurrency cap, data-quality queue, (5) alert rules on the thresholds the dashboards only encode as colours.

### A01 Column-entry trigger poller (generation 1, github-project-ai)

- **Was sie tut:** Polls one personal Projects v2 board every minute via GraphQL (all items, 100 per page: content type issue/PR/draft, state, labels, repository, single-select values with update time) and queues a job only when a card's Status CHANGES from another option into the configured option 'Ready for AI'. First run stores a baseline so cards already in that column never fire. Event key = sha256(item id + status-update time + option id), UNIQUE in SQLite: a repeated poll is a no-op, a later re-entry is a new job. Rejected with logged reason and a 'rejected' job row: draft items, PRs, closed issues, repos outside a 3-entry allowlist (each with SSH clone URL + starter wrapper).
- **Auslöser und Eingaben:** systemd user timer every minute (5 s random delay, Persistent) -> oneshot service (2 h timeout, NoNewPrivileges, PrivateTmp). Input config.toml: [project] owner/number/node id/title/url; [status] ready_name, field id/name, option ids; [runner] enabled, dry_run, poll_interval_seconds (never read by the code), max_attempts=3, create_pull_requests; [[repositories]] name/clone_url/starter.
- **Ergebnis und Zustand:** SQLite state.sqlite3 (WAL, 0600): meta, item_state(item_id,status,status_updated_at), jobs(event_key PK, item_id, issue_number, repo, title, status pending|running|retry|failed|completed|rejected, attempts, available_at, branch, workdir, pr_url, result, error_code). Rotating runner.log (2 MB x 5). Observed 2026-10-25 11:32 to 2026-10-26 08:32: 1,219 poll lines, 13 rejection lines (3 distinct events: 9 foreign repo, 4 non-issue/closed), 2 real jobs, 0 completed.
- **Fehlerbehandlung:** GraphQL error/timeout aborts the tick (exit 2; CLI stderr deliberately never logged); flock LOCK_NB single instance; interrupted 'running' jobs become retry; back-off min(3600, 30*2^(n-1)) s; after max_attempts failed and, only if such an option exists, Status 'Blocked'; 'retry <event_key>' requeues; offline self-test simulates baseline / transition / duplicate / other status / re-entry / foreign repo / lock.
- **Externe Systeme:** GitHub GraphQL/REST through gh CLI (stored login; GITHUB_TOKEN/GH_TOKEN stripped from child env), git over SSH, Copilot CLI wrappers.
- **Abstraktion für das Produkt:** Column-entry trigger on a pipeline: 'run this pipeline when a card ENTERS lane X'. Needs baseline on enable (existing cards do not fire), idempotent entry key per (card, entry time), source/repo allowlist, rejection log with reasons, single-flight lock, bounded retry with exponential back-off, manual requeue, dry-run/enabled flags and an offline self-test of the trigger semantics.
- **Beleg:** ~/bin/github-project-ai (record_items, process_jobs, simulate, database); ~/.config/github-project-ai/config.toml (+2 .bak copies); ~/.config/systemd/user/github-project-ai.{service,timer} (timer absent from timers.target.wants = not enabled); ~/.local/state/github-project-ai/{state.sqlite3,runner.log}; ~/docs/github-project-ai-automation.md; ~/docs/automation-architecture-activity-audit.md sections A, B.

### A02 Board schema pinning, drift detection and guarded activation

- **Was sie tut:** 'resolve' finds the one single-select field that contains the ready option and stores project node id, field id and the full option-name->id map in the 0600 config (timestamped backups). Every tick re-reads the board and refuses to run if project id, status field id or the option map changed ('re-resolve'). 'snapshot' prints project/field/item inventory read-only. 'install' = verify starters and gh login -> offline self-test -> resolve -> snapshot -> baseline -> flip config to enabled -> enable timer; if the timer is not active it disables it and returns the config to enabled=false/dry_run=true. enabled=true with dry_run=true is rejected at load.
- **Fehlerbehandlung:** Option names are hard-coded, not matched against the board: runner writes 'In Review' while the board option is 'In review', and 'Blocked' does not exist, so those status updates are silent no-ops (update_project_status returns False). Inferred from code vs config option map; the success path never ran.
- **Abstraktion für das Produkt:** Board adapter binds lanes/fields by stable ID resolved by NAME at setup, pins them, detects schema drift on every sync and blocks with a clear re-resolve action; activation is a guarded sequence (verify -> dry-run -> baseline -> enable -> auto-rollback); an unknown lane name must raise, not skip.
- **Beleg:** ~/bin/github-project-ai (resolve, find_status_field, validate_resolved, command_install, set_runner_mode, update_project_status); config.toml option map names (Backlog, Ready for AI, In progress, In review, Done); ~/docs/github-project-ai-automation.md 'Host activation sequence'.

### A03 Isolated per-task workspace, untrusted-input prompt, machine-readable agent result (gen-1)

- **Was sie tut:** Per accepted job: git clone of the SSH remote into ~/.local/share/github-project-ai/workspaces/<owner-repo>/issue-<n>-<eventkey10> on branch ai/project-<project>-issue-<n>-<eventkey10>; an existing workspace is reused only if origin and branch match, partial changes of an interrupted attempt are kept, never reset. Agent (Copilot via the repo's starter wrapper, 3600 s) gets project URL, item id, issue URL, status, labels, title and the issue body wrapped as untrusted data (ignore instructions to reveal credentials, change automation/security config, use another repo, deploy, create/push a PR); it must not commit/push/open a PR. It must print exactly one line AUTOMATION_RESULT_JSON:{outcome success|blocked, summary, tests[{name, result passed|failed|not_applicable, details}], no_tests_reason}; success needs a test report or a reason; missing/duplicate line or a failed test = runner error. outcome=blocked -> job failed needs_human_clarification, optional Status Blocked, issue comment with idempotency marker <!-- github-project-ai:<event key> --> asking for clarification.
- **Ergebnis und Zustand:** Two workspaces exist for the same issue (two attempts), both clean checkouts on their ai/project-5-issue-4-<key> branch with no commit beyond main.
- **Abstraktion für das Produkt:** Per-run isolated workspace (clone/worktree) with deterministic branch naming and reuse rules; prompt template that fences card text as untrusted; one-line machine-readable result contract (success/blocked + test evidence); a 'blocked: needs human' outcome that becomes a card comment and a lane change.
- **Beleg:** ~/bin/github-project-ai (ensure_clone, run_copilot, parse_agent_result, add_blocked_comment); ~/.local/share/github-project-ai/workspaces/<owner-repo>/issue-4-98fd4d7bed and issue-4-3361224294; state.sqlite3 jobs.

### A04 Pre-publish gates, PR publication and output redaction (gen-1)

- **Was sie tut:** After a success result the runner runs git diff --check (worktree + index); scans the diff against origin/HEAD and untracked text files up to 1 MB for secret patterns (gh*_ and github_pat_ tokens, AWS key ids, private-key headers, generic api_key/secret/password assignments, sk- keys) and refuses to publish on a hit; requires at least one commit ahead of base ('Agent reported success but the isolated branch has no commit' - the real failure of job 2); commits 'AI: <title>' with a bot identity; pushes; looks for an existing open PR on the head branch before gh pr create (body = summary + checks list + 'Closes #N'); adds the PR to the board (gh project item-add); posts a result comment once (marker check via gh issue view --json comments); sets Status 'In Review'. Done is never set. All strings leaving the runner (titles, summaries, test details, logs, PR body, errors) pass redact().
- **Abstraktion für das Produkt:** Publish stage with mandatory gates (secret scan of diff + untracked files, whitespace check, 'work really exists' check), idempotent PR creation and card linking with a closing keyword, idempotent result comment, one redaction filter for everything that leaves the system; the terminal lane is human-only.
- **Beleg:** ~/bin/github-project-ai (scan_for_secrets, publish_success, existing_pr, link_pr_to_project, add_result_comment, redact, SECRET_PATTERNS); state.sqlite3 job rows; ~/docs/automation-architecture-activity-audit.md F.7 (scan_for_secrets judged reusable).

### A05 Run-start signal: label + bot assignee (two-key guard) with ordered start

- **Was sie tut:** A run of the active pipeline starts only when the issue carries label ai:ready AND is assigned to the bot account aiForgeAgent; per owner notes plain comments never start runs and marked agent comments are ignored by design. Start order is assign first, label last, because the guard evaluates the 'labeled ai:ready' event and needs the assignee already present. Terminal shortcut aiforge-start <n> [owner/repo] checks the issue is OPEN, then gh issue edit --add-assignee aiForgeAgent --add-label ai:ready. GitHub-side shortcut label ai:go does the same via n8n (reset ai:ready, assign bot, unassign human, sleep 2 s, set ai:ready, remove ai:go). Autonomous follow-ups and ai:accept/ai:slice 'run' mode re-arm both keys themselves. Owner rule: never create issues with ai:* labels or the bot assignee (starts the pipeline); a 'stalled' run after an answered question usually means the keys were toggled off.
- **Auslöser und Eingaben:** GitHub issue webhooks (human origin) or scheduler/autonomous payloads; pre-gate switch in n8n workflow GitHub.Agentic.Coding.
- **Abstraktion für das Produkt:** Explicit run-start signal with a two-condition guard and defined ordering, startable from UI, CLI and API/MCP (a Start button = the same signal); the origin of a start (human vs autonomous) is recorded and used by triage; plain comments never start anything.
- **Beleg:** ~/bin/aiforge-start; n8n GitHub.Agentic.Coding nodes 'Switch: Pre-Gate', 'Code: ai:go Command'; ~/.claude/projects/-home-orologas-codeman-cases-testcase/memory/netrats-pipeline-trigger-labels.md; ~/codeman-cases/testcase/uebergabe-naechste-session.md ('Regeln des Nutzers'); ~/codeman-cases/testcase/handover-eigenstaendiges-pipeline-tool.md 3.2.

### A06 Human command labels: ai:go, ai:slice, ai:accept, ai:force

- **Was sie tut:** One-shot labels the automation consumes immediately (the event stays in the issue timeline). ai:go = normal start (triage runs first). ai:slice = human demands (re)slicing: the stage-handover table supplies next_action, then the same start sequence; no handover -> nothing starts. ai:accept = human accepts the current stage: mode ready (stage ends WITHOUT a run: package becomes ai:implementation-ready or, for the implementation stage, ai:implemented + board Done; all ai:*/human:* labels and both assignees removed; waiting dependent packages released; comment <!-- aiforge:accept -->), mode run (set next_action and start), busy (a step is running: only the reason is commented) or none. ai:force = skip triage for this start.
- **Abstraktion für das Produkt:** Human gate actions as one-shot commands (accept stage, re-plan, force run) that the engine consumes and logs; the stage->next-action mapping is data (stage handover rules) with modes 'end stage without a run' vs 'continue with action X'.
- **Beleg:** n8n GitHub.Agentic.Coding nodes 'Code: ai:go Command', 'Code: ai:slice Command', 'Code: ai:accept Command', 'DB: Accept Stage', 'DB: Stage Handover'; ~/bin/aiforge-triage (recent_command, ai:force); handover-eigenstaendiges-pipeline-tool.md 3.2; ~/codeman-cases/testcase/audit-agentic-coding-2026-11-09.md 5.1.

### A07 State and hand-over protocol: labels + assignee swap + board Status = who holds the ball and why

- **Was sie tut:** Claim: add ai:processing; remove ai:ready, ai:queued, human:review, human:question, ai:failed; remove the human assignee; board Status 'In progress'. Waiting for a slot: label ai:queued + Status Ready (queue reason global-cap). Hand-over after a valid result or stop: remove ai:processing/ai:ready/ai:queued, unassign bot, assign human, add ONE reason label - human:review (please check), human:question (decision needed), ai:pr-ready (epic PR waits for the human to merge), ai:failed + human:review (failed after last attempt), ai:gate-missing (mandatory gates still missing after n/max automatic follow-up runs, comment <!-- aiforge:gatecheck -->) - and set Status Ready LAST, after the trigger is gone. Sub-issue results add ai:implementation-ready / ai:implemented; ai:autonomous marks an autonomous follow-up. One REST call, fixed order: remove labels, remove assignees, add assignees, add labels (trigger label last); a missing label is not an error.
- **Fehlerbehandlung:** Hand-over shell commands end with '|| true' / '; true', so a failed GitHub call leaves labels/board stale (see lessons); the inbox is mirrored in the DB (A27).
- **Abstraktion für das Produkt:** Hand-over state machine per card: owner (agent|human) + reason (review|question|failed|pr-ready|gate-missing) + lane, changed atomically in a safe order; reasons drive a 'waiting for you' inbox and notifications.
- **Beleg:** n8n GitHub.Agentic.Coding 'SSH: Mark Issue Started', 'SSH: Mark Issue Queued', 'SSH: Mark Issue Failed (Coding)', 'SSH: Mark Issue Stopped'; GitHub.Agentic.Events 'Code: Handover Commands (Valid)', '(Failed)', '(WP Done)', 'SSH: Finish Sub-Issue', 'GitHub: Comment Gate Check'; ~/bin/aiforge-issue; ~/repos/Netrats/AGENTS.md; audit-agentic-coding-2026-11-09.md Anhang A (label list).

### A08 'Done' means clean slate; completion of epics belongs to the human

- **Was sie tut:** Setting board Status 'Done' through aiforge-project automatically runs aiforge-issue --clear: DELETE all labels and all assignees (REST as bot) and drop the issue's handover rows; callers must set Done as their LAST step (opt-out env AIFORGE_DONE_KEEP=1). Work-package sub-issues get Done when implemented/accepted; epics are never set Done by hand-over: they end at ai:pr-ready and the human's merge of the PR ('Closes #N') closes them. The gen-1 runner never set Done; the monitor agent must not set Done ('reserved for the author after acceptance').
- **Abstraktion für das Produkt:** Terminal-state rule: completing a card strips every pipeline signal so nothing can re-trigger; parent completion is driven by a human merge/acceptance, child completion by verified results; agents and monitors can never move a card to Done.
- **Beleg:** ~/bin/aiforge-project (end of file), ~/bin/aiforge-issue (--clear), n8n GitHub.Agentic.Events 'Code: Handover Commands (Valid)' comment text, ~/repos/Netrats/.squad/ralph-instructions.md 'Project Status Integrity', ~/docs/github-project-ai-automation.md.

### A09 Board column vocabulary across generations

- **Was sie tut:** Status single-select vocabulary actually used. Gen-1 board (Project 5 'netrats', config.toml): Backlog, Ready for AI (trigger), In progress, In review, Done. Writing pipeline (Netrats scripts/issue-workflow.sh, AGENTS.md, run-profiles.md): Backlog, Queued (global cap or autonomous restart), In Progress (claimed), Waiting (handed back to the human; 'blocked' = Waiting + label status:blocked), Done. Coding board (Project 7 'agentic.Coding', n8n nodes): Ready = queued OR handed to the human (written last, after trigger labels are gone), In progress = run started, Done = work package implemented/accepted. Legacy gateway: Status Ready + State unclaimed beats Backlog + State processable.
- **Abstraktion für das Produkt:** Lane model: Backlog (not admitted), Ready/Queued (admitted, waiting for slot or human), In progress (agent working), Waiting (human holds the ball), Done (terminal). Lanes are written by a single writer (engine); humans only admit (Backlog->Ready) or accept (->Done).

### A11 Run counter sync (derived metric written back to the board)

- **Was sie tut:** systemd timer every 2 min runs aiforge-sync-runs: reads view issue_run_counts (per repo+issue: laeufe = distinct minutes of queue entries of kind new or comment = human starts; wiederherstellungen = recovery entries; letzter_lauf; writing use case only), pages all board items via GraphQL (100 per page, fieldValueByName), compares with the current 'Läufe' number and writes only changed values, 15 aliased updateProjectV2ItemFieldValue mutations per request; issues without runs stay empty. ### A12 Board field helper with ID cache (aiforge-project)

- **Was sie tut:** get <owner/repo> <issue> returns {itemId, fields{name:value}} (single select as option name, text, number; issue not on the board -> itemId null, exit 0) from ONE GraphQL query over the issue's projectItems filtered to the configured owner/project (default project 7). set <owner/repo> <issue> <field> <value> adds the issue to the project if missing, resolves field type / option id / data type and writes text, number or single select (empty value clears); project id, field list, data types and item ids are cached in ~/.cache/aiforge-project/<owner>-<project>.json so a cached set costs 1 GraphQL call instead of 4; stale ids (field recreated, item removed) drop the cache and retry once; unknown field/option -> exit 1. Uses the human's gh login because the bot token has no project scope.
- **Abstraktion für das Produkt:** Board/forge adapter with ID caching, retry-once on stale IDs, typed field writes, auto-add of cards and an explicit API-call budget.

### B01 Multi-source usage ingestion into one ledger

### B03 Dual cost accounting (billed vs notional) with provenance and resolution status

- **Was sie tut:** actual_cost = what the provider billed/reported (OpenRouter generation usage, AI Hub spend, OpenCode message cost when > 0, LiteLLM cost when present; may be 0 for free tiers); shadow_cost = notional list-price estimate for calls without billing (free tiers, subscription plans, sovereign models). ### B04 Versioned price book and cost formula

- **Was sie tut:** pricing_model: one row per canonical model with validity windows (valid_from inclusive, valid_to exclusive, NULL = open; EXCLUDE gist constraint forbids overlaps per model), original prices + override prices (override wins; 0 = really free; NULL = no override) in five dimensions input / output / reasoning / cache read / cache write (USD per 1M tokens); is_reference marks models whose prices are auto-fetched from the OpenRouter catalog (timer: price refresh daily 03:15, model discovery 04:00). canonical_pricing_lookup(model, at) returns effective prices. compute_shadow_cost = round(((input - cache_read - cache_write) x in + cache_read x cr + cache_write x cw + output x out + reasoning x reasoning) / 1e6, 7); cache/reasoning prices default to input/output price when unset; NULL when no price contributes. Legacy flat pricing table, alias registry and 4 backup tables were removed (migrations 012/013).
- **Abstraktion für das Produkt:** Versioned price book per canonical model with validity windows, per-dimension prices, manual override layer and automatic catalog refresh; cost computed at ingest from the price valid at request time; recompute/backfill jobs.

## Schmerzpunkte und Lehren

- GRAPHQL BUDGET (2026-11-08): the human login's 5,000/h GraphQL limit was exhausted by aiforge-project (4+ calls per set) and gh issue edit; hand-over commands end with '; true', so failures were swallowed and labels/board stayed stale (#105: ai:ready stayed, the gate ran twice). gh api rate_limit showed stale values; only the X-Ratelimit-Remaining header of a GraphQL call is reliable. Fixes in place: ID cache (1 call/set), REST + bot token for labels/comments, batched mutations (15 per request), change-only writes. Requirement: forge adapter with call budgeting, REST-first, batching and surfaced side-effect failures. [memory github-graphql-rate-limit-pipeline.md; aiforge-project; aiforge-sync-runs]
- NEVER SWALLOW ERRORS: owner rule after silent hand-over failures - every automatic decision or failure needs a decision-log entry and a visible card comment; tools that must not block a hand-over (epic-pr, runlog, merge-check, epic-delta) exit 0 but report on the card. [handover-eigenstaendiges-pipeline-tool.md 6/7; aiforge-epic-pr]
- START-SIGNAL SAFETY: a label alone is too easy to set by accident; hence two keys (label + bot assignee), 'assign first, label last' and a 2 s pause; creating issues with ai:* labels is forbidden; a 'stalled' run after an answered question usually means ai:ready/assignee were toggled off. [aiforge-start; memory netrats-pipeline-trigger-labels.md]
- GEN-1 POLLER FAILED QUIETLY: in ~21 h it logged 1,219 empty polls, queued 2 jobs (needs_human_clarification; 'success' without any commit x3), completed 0, and was superseded within 6 days, leaving a disabled timer, workspaces and config backups; no shared state with gen-2 although both served the same boards/repos. Lessons: verify that a commit exists instead of trusting the agent's 'success'; do not run two uncoordinated automations on one board; keep config knobs wired (poll_interval_seconds is unused). [state.sqlite3, runner.log, automation-architecture-activity-audit.md]
- HARD-CODED STATUS NAMES are silent no-ops: runner writes 'In Review' but the board option is 'In review', and 'Blocked' does not exist (inferred from code vs config). Resolve option IDs by name at setup, validate, fail loudly.
- BOARD FIELDS AS ORCHESTRATION STATE did not scale (GraphQL cost, drift): Stage/Action/Iteration/Next Action were moved into the DB; the board keeps Status, Run Profile, Läufe. Personal-account Projects v2 have no webhooks, so board-entry triggers need polling. [GitHub.Events node comments; github-project-ai-automation-audit.md]
- STATUS/LABEL DRIFT with several writers: n8n is declared single writer; a read-only monitor reports mismatches; a PR-event guard workflow and a manual repair script exist; Done strips all labels/assignees so nothing re-triggers. A product should have one writer plus a reconciliation report. [Netrats AGENTS.md, ralph-instructions.md, squad-status-guard.yml]
- INBOX CORRECTNESS: 'waiting for you' depends on a label mirror; the sync only updates labels it sees, so vanished labels must be deleted explicitly or the card stays 'waiting' forever; reconcile conservatively (keep the old state on GitHub errors). [aiforge-handover-sync; control-center doc 5 B]
- COMMENT PAGINATION TRAP: GitHub returns 30 comments per page, oldest first; agents read page 1 and reported 'no new comments' while the newest decisions sat on page 2 (Netrats#38). Mitigations: hook plugin forces per_page 100 + hint, AGENTS.md demands all pages, aiforge-comment list pages everything; comment size cap 65,536 chars -> run log trimmed at 60,000. [aiforge-hooks.js, AGENTS.md, aiforge-runlog]
- RESULT-CONTRACT VIOLATIONS COST A WHOLE CYCLE: the validator now also runs inside the posting tool so the agent can fix in-run, but it exists twice (script copy of the n8n node, 'regenerate by hand') - ship one implementation. [aiforge-comment-contract.mjs header]
- MARKER DISCIPLINE: the engine tells agent comments from the author's only by the marker line; an unmarked agent comment is treated as human input; marked comments never start runs. [Netrats AGENTS.md]
- IDENTITY LIMITS: the bot token has no Project scope, so Projects use the human login (and its GraphQL budget); commits must carry the human identity for a deploy platform; tokens leaked several times -> vault, masking, no secrets in agent env (shared tmux server leaks env); the audit names a GitHub App as the replacement. [opencode-aiforge, audit-agentic-coding section 6, handover doc section 7]

[uebergabe-naechste-session.md]
