## 1. n8n: Ereignis-Eingang und Coding-Ablauf

The coding pipeline is a label/assignee-driven, DB-queue-backed state machine over GitHub issues, with Postgres (schema github_automation + prompt_evolution) as the source of truth and GitHub only as UI/trigger.

TWO MAIN WORKFLOWS (both active)
1. GitHub.Agentic.Coding = "intake + launcher". Triggers: (a) GitHub issues webhook /agenticCoding (HMAC-checked, observation mode only, never blocks); (b) internal webhooks /agenticCodingWake (wake the queue) and /agenticCodingRetry (re-enqueue a follow-up/retry). A Switch filters events: ai:ready label (or aiForgeAgent assignment) on an issue labelled epic or work_package AND assigned to the agent => start; label ai:go => shortcut that re-labels/assigns and thereby re-fires ai:ready; ai:slice => manual stage transition; ai:accept => user accepts a stage. Start path: expire stale queue rows (>3h inactivity) -> resume-check script (health-pause needs a user reply) -> upsert issue + enqueue (unique partial index prevents double enqueue) -> claim oldest runnable queue row (FIFO, FOR UPDATE SKIP LOCKED, dependency check deps_met) -> acquire global server slot (max_active_runs) -> read board fields -> optional triage script -> resolve action (recovery prompt > issues.next_action > start action of artefact type) -> load routing rule (stage, agent, model, run profile, temperature, branch mode, runtime/stall/watch limits) -> load work package -> resolve model via run-profile endpoints/cluster -> abort/close older active sessions of same chain -> create git worktree (+epic branch) -> create a Codeman (tmux) session -> render system/user prompts from versioned DB prompt configs -> register session row BEFORE launch -> write prompt files into the worktree -> launch OpenCode CLI inside the tmux session with env vars (session id, stall ms, max runtime, expected result files, action, watch interval) -> wait up to 120 s for a "prompt submitted" hook event -> mark processing, set labels ai:processing / board Status In progress.
2. GitHub.Agentic.Events = "supervision + result reading + next-step engine". Trigger: POST /copilotEvents (hook events from the CLI plugin: sessionStart, userPromptSubmitted, postToolUse, agentStop, stopFailure, errorOccurred, preCompact, loopAbort, sessionEnd, heartbeat). Every event is logged (copilot_events) and mapped to issue/session. For coding runs, agentStop/stopFailure/sessionEnd on an active session atomically claims the run (session active->closed), kills the tmux session, removes the worktree, reads the result (agent comments with a marker line, or a JSON result file in the worktree, or a deterministic check script), validates the output contract, discards invalid comments, and either retries (max 3 attempts), or decides the next step from routing rules (Decide Next), writes next_action, hands over to the human, or schedules work packages. Errors in the workflow itself are caught by an n8n error workflow, which fails the queue row/issue and hands over to the human.

SUPPORTING WORKFLOWS: InternalReentry (HMAC re-signing forwarder so internal re-entry is accepted by the public webhook), Copilot.ToolGuard (PreToolUse hook loop guard), execution.Gate + GitHub.Gateway (older board-polling dispatcher with a DB-less lock table), GitHub.SetProjectField / IsCompletion / UpdateLabels / PrepareAgentContext (older sub-workflow helpers for project fields, parent-completion, labels, prompts), DB.AgentManagement (LLM that creates/updates agent prompt configs in the DB with an LLM goal-gate), commitDiggest (separate commit-digest + prompt-optimizer prototype), tmp-aiforge-errtest (inactive test that deliberately throws to test the error path).

ISSUE/ARTIFACT STATE MACHINE (reconstructed)
Artefact types: epic and work_package (WP). Pipeline stages per type (from stage names in code): epic-refinement (epic-gap-analysis -> gate -> optional epic-gap-resolution, with on_empty_action skipping resolution if no open points) -> epic-slicing (wp-slicing -> wp-slicing-gate; on pass seeds the work_packages table, creates one sub-issue per WP, relinks [[WP-x]] placeholders to issue numbers) -> per sub-issue wp-refinement (wp-build -> wp-build-gate [creates WP body]; wp-review -> wp-review-gate -> wp-apply -> wp-apply-gate loop; exit when implementation-readiness >= threshold (default 95) and no blocker/critical/high, or rule-based exit after N review cycles, optional independent confirmation review wp-review-confirm) -> implementation (wp-implement with OAC OpenCoder agent -> deterministic check script (impl-check) -> wp-implement-gate -> optional wp-code-review [-gate]; failures loop back to wp-implement with verbatim failures) -> implemented (ai:implemented, board Done) -> epic finalisation (epic-finalise: delta analysis) -> epic-document (PR text; handover_command opens the epic PR; label ai:pr-ready) -> merge (epic-merge-resolve). Health watchdog actions (X-health) run every N cycles of a loop and return continue / accept / pause.
Per-run states: queue.status pending -> claimed -> processing -> done | failed (also waiting); session.status active -> closed | failed; issue.state queued -> processing -> done | failed. Labels: ai:ready (trigger), ai:queued, ai:processing, ai:failed, ai:autonomous, ai:implementation-ready, ai:implemented, ai:pr-ready, ai:gate-missing, human:review, human:question, commands ai:go / ai:slice / ai:accept; assignee aiForgeAgent = agent owns it, human owner = human owns it. Board Status: Ready / Queued / In progress / Waiting / Done.
Handover to human: remove ai:* labels, remove agent assignee, add human assignee, add human:review (or human:question when the last marked agent comment is a question/answer), board Status Ready; the human resumes by setting ai:ready again (or ai:accept / ai:slice / ai:go); after a health pause ai:ready requires a new user comment.

**Schmerzpunkte und Lehren**

- Duplicate/looping starts are the dominant failure class: the unique partial index uq_queue_coding_open_per_issue, the 3 h stale-expiry, the DO NOTHING enqueue, and the 'Sicherung (2026-11-10, Schleife #120)' guard that refuses to restart a cycle_start action of an already-completed stage all exist because next_action was cleared and the start-action fallback sent WP #120 (Epic #106) back to wp-review about 20 times. DB: Save Next Action now refuses to clear next_action while another 'new' row exists. Lesson: next step must be explicit state, never a fallback; one open run per card/chain must be enforced by the data layer.
- Races between webhook-driven steps: stage end enqueues the next stage and may be claimed within a second, hence the 'keep next_action while a row of another run exists' rule; duplicate agentStop events are neutralised by an atomic claim (session active->closed in one UPDATE ... RETURNING); recovery/breather decisions use unique indexes per Codeman session; wake calls are capped at 6. Lesson: claim run-end atomically and make every decision idempotent.
- Killing a run causes a second event: old sessions are closed in the DB BEFORE the tmux session is deleted so the killed process's sessionEnd is ignored (and a 'lost' detection that checks last prompt vs last top-level agentStop). Lesson: close state first, then kill; ignore late events from superseded sessions.
- Session registered before launch so early hook events map to it; start is verified by waiting for userPromptSubmitted (120 s); otherwise failure. Lesson: a launch is not successful until the agent proves it received the prompt.
- Shared opencode server leaked about 250 MB per session; replaced by one OpenCode process per run in its own tmux session (Codeman), with the recycle node left disabled and orphan finders as a safety net. Lesson: per-run process isolation, explicit reaping of orphans after crashes/kills, never touch user-owned sessions.
- AI gateway (LiteLLM/ai-hub) aborts streams at random: same-route retry (2x, 20 s pause) before switching endpoints; model chain per cluster with fallback cluster, then Claude Sonnet as last line of defence, then give-up with a human handover that keeps the session alive so the next human comment goes straight into it. Lesson: separate transient provider faults from model behaviour (loop abort and context loop never retry on the same model).
- Agents ignore deny messages and loop: tool-call fingerprint guard (4th identical call denied, 3rd denial aborts the run), edits count as progress; polling/read-only tools exempt; file writes through bash are not recognised (documented limitation). Lesson: guardrails need progress awareness and escalation to abort.
- Context saturation: 10 compactions without subagent progress => 'breather' (fresh conversation, max 3), then normal recovery; a context loop is not helped by resuming the same conversation (freshSession). Lesson: detect context loops and restart with state reconstruction.
- Output format drift is the second-largest cost: results are parsed out of GitHub comments by exact first-line marker and per-action schemas; invalid comments are rewritten to '<!-- aiforge:discarded -->'; retries limited to 3; many contract rules (wp slicing consistency, readiness line = JSON value, AK/TC criteria table, apply.json strict keys). The 'proposedChange only on rejected/open_decision/unresolved_gap' normalisation and wp.md heading generation by the pipeline (never the model) show that deterministic normalisation beats retrying. The OAC runs and gates write JSON FILES in the worktree because comment parsing was brittle. Lesson: structured output channel, deterministic normalisation, and lint scripts the agent runs on itself (aiforge-wp-lint) before finishing.
- Readiness percentages fluctuate (a medium finding produced 95 % and 90 %), so a rule-based exit (no blocker/critical/high; mediums only after N review cycles) and an independent confirmation review were added. Review loops are unbounded by count and are bounded only by the health gate; the health gate needs a reset (health_reset_at) after a human answers. Lesson: quantitative LLM scores are unreliable gates; keep a progress watchdog.
- Human handover state is encoded in labels+assignee+board status across 3 systems; helper scripts always end with '|| true' (label failures never fail the pipeline) and the sequence matters (remove labels, then assignees, then add; board Ready LAST after the trigger labels are gone; 'sleep 2' between assign and ai:ready so the assignment is visible). Lesson: single source of truth for ownership/state inside the product; no label toggling tricks.
- Health pause requires a user reply before ai:ready is honoured (aiforge-resume-check posts <!-- aiforge:resume-blocked -->). Lesson: a pause needs an explicit answer capture, not just a re-trigger.
- Handover tracking was added for Grafana (handover_open) because GitHub could not be queried cheaply; the Grafana dashboards (AI Usage, AI Pipeline Control Center) are fed by DB tables sessions, queue, copilot_events, handover_open, wp_findings (inferred: dashboards not inspected in this slice).
- SECURITY pain points (values intentionally not reproduced): a GitHub personal access token is embedded in plain text in nodes of GitHub.Gateway, GitHub.SetProjectField and GitHub.IsCompletion; a shared 'internal re-entry' token is hard-coded in several Events code nodes (comment says it must match the guard node); HMAC verification is observation-only so forged webhooks are not rejected; SQL in DB.AgentManagement and PrepareAgentContext is built with string interpolation of LLM/webhook values. Lesson: product needs a secret store, enforced signature verification and parameterised queries.
- Operational debt: the workflow carries a legacy writing/Copilot branch (gate checks, integration cherry-pick, Claude review, autonomous follow-up) alongside the coding branch, selected at runtime by use_case; WEBHOOK_PATHS maps both; duplicate worktree teardown scripts exist (normal + give-up); execution.Gate lock is inserted but never visibly released (crash leaves RUNNING, inferred); GitHub.UpdateLabels is inactive and replaced by helper CLIs; tmp-aiforge-errtest is an inactive test hook. Lesson: model use cases as pipeline definitions instead of branching inside one workflow.
- The n8n workflows are only the orchestration layer: most real logic lives in local scripts under /home/orologas/bin (aiforge-issue, aiforge-project, aiforge-comment, aiforge-runlog, aiforge-wp, aiforge-resume-check, aiforge-triage, aiforge-impl-check, aiforge-epic-check, aiforge-epic-delta, aiforge-review-context, aiforge-wp-manifest, aiforge-wp-lint, aiforge-wp-worktree, aiforge-worktree-sweep, opencode-aiforge, aiforge-session-watch) and in Postgres functions (acquire_server_slot, deps_met, wait_run_event, wp_start, wp_stage_end, accept_stage, ledger_update, next_endpoint, chain_remaining, aiforge_wp_dep_ok). Their code was not inspected here; the product needs equivalents as built-in actions.
- Timezone and API quirks documented in code: REST 'since' filter unreliable around DST changes (comments are filtered client-side); Codeman rejects session names over 100 characters; --prompt argument limited to ~128 KiB (guard at 120000 bytes); SSH node does not fail on non-zero exit so exit codes are checked in Code nodes; prompts/comments travel base64-encoded to avoid shell interpolation; @-mentions neutralised in error comments to avoid notifying people.

## 2. n8n: Planung (Epics, Work Packages) und Schreiben

The planning/writing pipeline is a chain of webhook-triggered n8n workflows that move a GitHub issue (an Epic, a Work Package, or a manuscript outline) through stages. A GitHub Project item carries the routing contract (fields: stream, stage, action, strategy, artefaktType, promptKey, gitBranch; status Backlog/Ready/In Progress; state processable/claimed/unclaimed; a processingLock.run_id row in a data table workflow_execution_locks). The Gateway posts the item to /analysis or /refinement, which route by stage x action.

PLANNING (software): (1) Epic Clarification: AI gap analysis of the epic produces a questionnaire split into manual questions (human) and autonomous ones; asked one by one in a dedicated Slack channel. (2) Stakeholder answers are semantically mapped to questions (open/partial/answered) in Redis; when none is open, Decision Integration rewrites the Epic issue body into a structured epic spec. (3) Epic Slicing: a repo-evidence manifest is built (AI picks relevant files from the tree, a goal gate validates, files are fetched), an Initial Slicer proposes Work Package candidates, a Slicing Quality Gate accepts/rejects. (4) EpicWPRefiner recursively (max depth 3) runs an Atomicity Gate per WP and, if too big, decomposes into child responsibilities, each specified into a full structured WP. Final WPs become GitHub sub-issues of the epic, are added to the Project board and parked at stage Review / action Create Review. (5) Review loop: CreateReview (AI requirements review with severity/confidence/blocker + AI quality gate deciding whether to continue) posts a versioned comment; ApplyReview (AI applies every finding with a per-finding change log + an AI gate that decides whether the output may replace the WP) loops back to CreateReview until the gate says stop, then the item is released as Ready for the Implementation stream.

WRITING (manuscript): author hints per sequence -> Outline Elaboration (Sequence Builder agent + Goal Gate PASS/RETRY/BLOCKED + commit-message agent + Slack human approval) commits a sequence/scene/beat JSON outline to the repo -> Narrative Outline Review (reviewer agent + goal gate) -> Narrative Outline Refinement (refiner agent with change log + commit message + goal gate + Slack approval) commits the revised outline. Continuity review per sequence (inactive) and Scene Block Writing (active but only a skeleton that flattens scenes into word-count blocks) prepare prose writing. Agentic.Writing is the queue/launcher that hands a writing issue to an external CLI agent in a Codeman tmux session in its own git worktree.

Cross-cutting: prompts are loaded from a versioned Postgres prompt store (agent_key, system/user, blocks identity/task/context/constraints/knowledge/examples/runtime/output with node references); every LLM step is wrapped by structured-output parsers with auto-fix; nearly every generative step is followed by a separate LLM gate; retries are counters carried in the payload; a prompt self-optimisation loop exists but is inactive. Control flow is webhook chaining, with state in GitHub (issue body, comments, labels, project fields), Redis (Q&A), Postgres (queue, prompts) and Slack.

**Schmerzpunkte und Lehren**

- Silent dead ends: retry limits (EpicSlicing, CreateReview, ApplyReview, CreateManifest) end on an empty branch while the card stays claimed In Progress; rejected human approvals also end silently. The product needs explicit terminal states (failed/blocked/needs-human), a visible reason, and a healer/timeout for stuck claims. Evidence: If 'Retry Limit Exceeded?' nodes with empty true output; 'If1' in OutlineRefinement.
- Retries and loops are encoded as webhook re-POSTs with counters in the payload or execution.customData (aiRetries, retryCount, refineWorkPackageRetryCount). Counters reset when state is lost, differ per workflow (3, 5), and some loops have none (Outline Elaboration/Review RETRY, review-apply rounds). Lesson: a run record with persisted attempt counts, per-step max attempts and a global max-rounds guard.
- Hard-coded credentials and secrets inside node parameters (a GitHub bearer token in two GraphQL nodes in EpicSlicingContext and ApplyReview, a LangFlow key in SeuqnzeStart, an internal shared-secret header in Agentic.Writing) despite a credential store. Values intentionally not reproduced here. The product needs a secret store with references and an internal-call signature mechanism.
- ApplyReview write-back appears disconnected (Render, Update Issue Body, Build Final Payload, Notify have no inbound connections): after a refactor the accepted refinement may never reach the issue. Lesson: end-to-end test of every loop and an explicit 'artifact version written' state change that a gate can assert.
- Clarification loop is half-live: EpicClarification is active but Slack.StakeholderFeedback and Slack.IntakeGateway are inactive, so answers would not flow back to DecisionIntegration (inferred). Also Q&A state lives in Redis with 24h TTL (memory 48h) and is keyed by Slack channel name, not by card id; a pause or renamed epic loses the session. Product: persist Q&A on the card, keyed by card id, no TTL.
- Mixed German/English schemas and aliases show contract drift: open/offen, antworten/responses, titel/title, gitBrnach/gitBranch, userPromt, ecpicDecisionIntegration path, SeuqnzeStart name; code contains normalisers for both. Lesson: one versioned schema per artifact (question, finding, WP, change log) validated at the boundary.
- Structured output is unreliable on free/small models: every agent has a schema parser plus auto-fix parser, custom repair prompts, and 'do not output the schema/template' guards; gates explicitly check for template/echo/truncated outputs; 'Do not refuse because the review said FAIL' guard in Apply. Lesson: schema validation + repair + model fallback chain are core engine features; keep gate prompts focused on semantics, not JSON validity.
- LLM gates are everywhere and repeatedly told 'do not require perfection', 'do not rebuild the ideal answer': gate over-strictness caused loops (inferred from prompt wording). Gate decisions are not persisted. Lesson: gates need calibration knobs, recorded verdict + reason per round, and cheap deterministic pre-checks (e.g. validate manifest paths against the tree, check WP not empty) before an LLM judge.
- Hallucination controls that were needed: path-only reasoning for file selection and validation against the real tree; 'evolution drift' rules (no invented APIs, files, features) for slicing; findings must carry confidence verified/assumption/missing_context; canon contradictions vs new creative content vs missing evidence distinguished strictly in writing gates. Lesson: evidence-grounded outputs with explicit provenance fields.
- Cost/size: the same repo manifest is rebuilt at every review/apply round, all context (full file contents, full tree) is pasted into every agent and every gate prompt, no truncation or token budget seen. Lesson: cache and version the evidence pack per card, send references/tools (as the writing agents already do with getCurrentArtifact/getRepositorySourceContext tool nodes) and budget context.
- Repo-specific hard-codes: tree filter allows only src/, docs/, tests/ and a few config files; fixed Project id; chapterId 'chapter-001'; a fixed file path in the outline approval branch; two workflows share webhook path narrativeOutlineReview in their inactive/active variants. Lesson: parametrise by project/pipeline configuration.
- Review history is stored as GitHub issue comments; review version = comment count + 1, 'latest review' = newest-updated comment: any human comment corrupts version numbering or is mistaken for the review (inferred). Lesson: typed review records with version numbers separate from discussion comments.
- Human approval via Slack sendAndWait has no timeout, rejection handling or feedback path; messages are cleaned by reading DM history and deleting. Lesson: an approval gate step with approve/reject/request-changes, comment returned into the next agent run, and a timeout/escalation.
- Sizing of work: the Atomicity Gate was added because slicing alone produced WPs too large for one autonomous run; depth cap 3 and 'fast vs smart' model variants show cost/latency tension. Lesson: atomicity is judged against the executing agent's capacity, with recursive decomposition and a depth limit.
- Writing pipeline learnings: the pipeline moved from LangFlow to n8n (disabled LangFlow branch), from a multi-agent supervisor (inactive 27-node) to single reviewer + gates + approval (active); author-persona prompts must not imitate living authors' voice; word-count budgets (scene 800-1500, block up to 2600, continuity blocks 1500-2500) drive structure; generation always requires canon evidence from repo files. Scene-block prose writing is not implemented yet.
- Launcher infrastructure lessons (Agentic.Writing, shared with coding): one issue per launcher slot, model cooldown after errors, stickiness, wake-on-release, worktree per issue to avoid shared working-tree conflicts, one-line prompt submission because CLIs submit on newline, HMAC signature in observe mode first, owner-only restart label. Failures at any start step must release the slot and hand the card back (Waiting).
- Self-optimising prompts were attempted but with weak evaluation (non-empty check) and a probable field-name mismatch; evaluation data (pinned sample WP/review in playground) is embedded in workflow JSON. Lesson: keep regression datasets of real runs and use rubric or pairwise evaluation before promotion.

## 3. Architektur-Dokumente und die beiden Generationen der Automatisierung

The documents describe TWO generations of automation around the same GitHub Project 5 (owner MichaOro; repos Netrats [a writing/novel-outline project], telemetry, vCardOrologas [coding]).

(1) "github-project-ai" (2026-10-25): a Python poller on a systemd timer (60 s) with SQLite state (meta, item_state, jobs). It watches the Project status field via GraphQL, enqueues a job only on an observed transition to the exact option "Ready for AI", clones the repo in isolation, runs a Copilot CLI starter, validates (structured result, git diff --check, secret scan), commits, optionally pushes/opens a PR, comments, sets "In Review" (never "Done"). Dry-run/baseline/enable flags guard activation. Audit (2026-11-19) finds it NEVER completed a job (2 failed jobs, both on Netrats#4: "needs_human_clarification" and "Agent reported success but the isolated branch has no commit"), timer disabled, last log 2026-10-26. Its only parts judged reusable: secret scan, lock pattern, idempotent transition ledger design.

(2) "AI-Forge" (first script 2026-11-01, active; 295 n8n executions on 2026-11-19, 99.3% success): n8n workflows (GitHub.Agentic.Writing = trigger/queue/launch, GitHub.Agentic.Events = session events/recovery/queue wake, Copilot.ToolGuard = loop guard) + PostgreSQL schema github_automation.* (22 tables: issues, queue, sessions, routing_rules [31 active rules, 8 stages], work_packages, epic_delta, scheduler_setting, triage_decision, session_watch, copilot_events 26k, tool_calls 28k, metric_history/autonomous_loop empty) + ~28 deterministic aiforge-* helper scripts + Codeman (tmux shell sessions) launching `opencode-aiforge --deepseek|--nemotron` (also copilot-squad and claude-opus as fallback) in git worktrees (epic/N, wp/N-issue-M, ai/issue-N). Results: 18 epics, 91 WPs, 84 implemented. Model: Epic -> gap analysis/resolution -> slicing into Work Packages -> WP build/refinement (review/apply cycles) -> WP implement -> code review -> epic finalise -> epic documentation (PR text) -> epic merge check -> PR (never auto-merged). Every stage is a routing rule (stage, action, agent_key, gate, handover_command, branch_mode, depends_mode) evaluated by aiforge-triage. Agents never decide quality: deterministic gate scripts and goal-gate/health-gate steps do. Communication with the human happens through machine-readable GitHub comments with HTML-comment markers (aiforge:progress/question/error/breather/gatecheck/epic-document/merge-needs-human) and issue labels (ai:ready, ai:go, ai:processing, ai:queued, ai:failed, ai:gate-missing, human:review) plus assignee switching (aiForgeAgent <-> MichaOro) as the hand-over protocol.

The owner's two assessment docs (feasibility vs reuse) disagree: the feasibility doc proposed building epic/WP/dependency/phase/iteration tables and a scheduler into the SQLite runner (READY_WITH_WARNINGS); the reuse doc, written same day, finds those already exist in the PostgreSQL pipeline and recommends only a bridge (Option A: epic-labelled items forward to the pipeline queue, others stay single-issue). The audit then concludes the old runner is a dead relic and AI-Forge is the real system. For openArtifact the consolidated reading: the product must reproduce Pipeline B's functions (stage routing table, queue with per-launcher slots, session supervision/recovery, deterministic gates, epic/WP hierarchy, comment contract, handover, epic branch + PR, worktree isolation, telemetry), plus the best ideas of Pipeline A (transition-based idempotent triggers, dry-run/baseline activation, allowlist, secret scan, never-auto-Done) and the owner's unmet requirements (dependency model, epic discovery, operator feedback/progress view, conflict UX, phase/iteration scheduling).

**Schmerzpunkte und Lehren**

- Pipeline A was built and then never produced a completed job: 2 failed jobs, both Netrats#4 ('needs_human_clarification'; 'Agent reported success but the isolated branch has no commit' x3). Lesson: trust platform-side verification of the diff, not agent claims, and prove one end-to-end run before enabling a timer (audit E.1, F.2).
- Two independent systems (SQLite poller vs n8n+PostgreSQL pipeline) served the same Project and repos with no shared state, scripts or trigger; duplicated concepts and a dead relic left loaded/disabled. The two same-day assessments contradict each other (feasibility says epics/phases do not exist; reuse says they fully exist in Postgres). Lesson: one engine, one data model; keep docs current; ask 'what already exists' first (audit D/E.3; reuse assessment 1).
- Activation of the first system was blocked by environment problems: invalid GITHUB_TOKEN exported in .bashrc (removed), sandbox could not reach api.github.com or user systemd bus; Codeman port clashed with Grafana (3000 vs 3001 fix). Lesson: credentials hygiene, preflight checks, explicit port management, safe-by-default config (enabled=false, dry_run=true) (github-project-ai-automation-audit.md).
- GitHub limitations drive workarounds: projects_v2_item webhooks only for org projects (hence polling); no native parent/dependency fields (labels or DB needed); MCP comments paginated 30/page oldest-first so models missed decisions on page 2 (Netrats#38). Lesson: first-class dependencies and a paging-safe activity feed in the product.

## 4. Parallele Work-Package-Ausführung

Status first: this is a built-but-not-live feature. The DB foundation and the Python scripts exist and pass 6 sandbox unit tests. The flag `parallel_wp_mode` is 0, Rule 26 is still `depends_mode=position-chain`, and the n8n Coding workflow patch is only a saved draft. The Events integration (validator and coordinator calls) is not implemented. The E2E audit (docs/parallel-wp-e2e-verification.md, 2026-11-19) rates it INCOMPLETE: no real parallel run ever happened. Everything below is therefore the designed functional model plus what the scripts actually do. Live production behaviour is still sequential. Source docs and scripts: ~/docs/parallel-wp-execution.md and the three deep-dive docs, ~/bin/aiforge-parallel-wp.py.

Intended lifecycle: (1) A planning agent cuts an epic into skeleton work packages. Each package has id, position, scope, acceptance items and a dependency list (`abhaengigkeiten`). Deterministic scripts check this (aiforge-wp-slicing, aiforge-wp-lint). (2) Packages are materialised as GitHub sub-issues (aiforge-wp) and as rows in work_packages. (3) The scheduler claims queue rows atomically (FOR UPDATE SKIP LOCKED plus deps_met). It reserves one of at most 2 OpenCode slots under a Postgres advisory lock. (4) A dedicated branch `epic/<N>-wp/<WP>` and a stable worktree per package are created from the epic branch. (5) The AI agent implements in that worktree. (6) A deterministic validator (impl-check against origin/epic/<N>) records the exact validated commit. (7) A per-epic merge coordinator merges validated packages in topological order with no-ff merges under a per-epic lock. It pushes the epic branch and marks the package `integrated`. Dependents unblock only on `integrated`. (8) When all packages are integrated, the existing epic stages run: epic-check, documentation, deterministic PR creation (aiforge-epic-pr), merge-resolve with a 5-check gate (aiforge-merge-check), and a human merge. (9) The sweeper removes worktrees and branches late and only when provably integrated.

Core design principles worth carrying over: agents never self-certify (every gate is a deterministic script); DB state is only advanced after Git proves it; every step is idempotent and resumable; feature-flagged additive rollout with legacy behaviour preserved; hard-to-undo steps happen last (the epic PR is merged by a human).

**Schmerzpunkte und Lehren**

- Branch-name collision: git cannot hold refs `epic/245` and `epic/245/WP-1` at once (ref file vs directory). Confirmed by a real worktree test. The product must pick a non-nested naming scheme (`epic/<N>-wp/<WP>`) for child branches. (docs/parallel-wp-execution.md)
- Original design had NO per-WP branches: branch_mode=epic-branch meant all WPs committed directly on epic/<N> in per-run worktrees, so true parallelism would cause same-branch git races. The serialisation came from n8n claim timing and triage routing, not from a DB guard. The product needs workspace isolation per card as a first-class concept. (assessment A)
- The early analyses were wrong twice: Evaluation 004 claimed the dependency checks were unused, but deps_met() was in the claim query. Later F-1 (slot undercounting by WP) was withdrawn once enqueue_wp was seen to use the WP's own issue number. Lesson: verify scheduler behaviour against live function source and rows, not documents. (technical-deep-dive 'Kritische Korrektur'; e2e-verification 14)
- 'created' status is not proof of integration. Four places (aiforge_queue_deps_met, DB: Load Work Package, wp_start, wp_schedule) treated it as sufficient. Also, 'done' could be reported while an accepted WP still awaited integration, which would close and hand over the epic before the merge. The product must define dependency satisfaction as 'merged and verified on the integration branch' and block epic completion while integrations are pending.
- Two disconnected state systems: DB status and Git reality can diverge (merge commit made but DB not updated, or the reverse). The solution is a marker in the merge commit message ([aiforge-wp:<id>]) plus ancestor checks to repair state. Never set 'integrated' by hand. The product needs an idempotent reconcile between its own state and the repository.
- Workflow wiring gap: scripts and DB layer exist but the Events workflow does not call validator or coordinator, and routing rules 27/36/28 still use impl-check or have no hand-over. It is unknown whether check_command/handover_command are executed generically with the needed arguments. Lesson: the pipeline's step hooks (check command, hand-over command with per-stage arguments) must be a generic, documented extension point, not hard-coded n8n nodes.
- Existing finished epics have no integration rows (Epic 245: 8 created WPs, 0 rows), so enabling the flag would regard them as unintegrated. Any new gate semantics needs a backfill or exclusion strategy.
- Slot accounting is easy to get wrong: active_runs() excludes the target epic and counts only the last 3 h of activity; acquire_launcher_slot ignores wp_id and overwrites sibling runs' launcher; slot function was originally called after worktree creation in the n8n Coding workflow (now before, per the audit). Locks need leases (15 min TTL) so crashed workers do not leak slots.
- Retry storms are costly: WP-6 of epic 255 was retried ~15 times (2-20 min each, about 4 h) before the epic was marked failed. Sequential position-chain compounds a failing WP. Motivates a max-attempts cap, cascade re-queue of dependents and early escalation to a human.
- Merge conflicts have no automatic resolution in the WP merge path: conflict means abort, status merge-failed, and the coordinator stops its pass. Risk of stale WP branches during long runs was noted (suggested rebase, not implemented). Possible mitigation proposed: file-scope declarations in skeleton 'enthalten' to detect overlapping packages and force them sequential (proposal only).
- Resource limits: OpenCode runs out of memory with 3 GB+ and has a hard 2-session cap; a recycle service restarts an idle, high-memory server. The product needs a resource-aware concurrency limit and a recovery service for runner processes.
- Models make contract slips (Chinese characters in German text, stale or duplicate review comments, wrong JSON enums). The answer was an agent-side lint that mirrors the pipeline's gate so errors are fixed within the run. Add 'pre-submit self-check' as a product pattern.
- Agents' own claims are never trusted: impl-check, wp-slicing check, merge-check and epic-pr are deterministic scripts with structured last-line results ('AIFORGE ... {json}') and exit codes. Hand-over steps (epic-pr) never fail the pipeline and report by comment instead.
- Hand-over and test constraints: no real parallel run has ever happened. Testing in production was blocked because creating an epic could trigger the live pipeline. A sandbox project with isolated triggers is a prerequisite for validating scheduler changes.
- Documentation drift: docs/parallel-wp-execution.md still states WP-7 #256 is processing although the audit found it done; the active workflow version pointer was never independently verified. Keep the status in the system, not in prose.

## 5. Hilfsskripte (deterministische Gates, Kontextbau, Betrieb)

The slice is a toolbox of small deterministic scripts that sit around the LLM agent runs of the owner's AI-Forge pipeline (n8n + GitHub issues and a GitHub Project board + Postgres schema github_automation + OpenCode runs inside Codeman/tmux sessions). They are not the orchestrator: n8n (workflows GitHub.Agentic.Coding / .Events / .Writing) calls them over SSH, the run launcher starts them as detached watchers, or systemd timers run them. They fall into seven families: (1) card-state primitives (labels, assignees, board fields, comments, run start, resume gate); (2) routing and self-healing (triage, healer, mode switches, decision log); (3) context builders that hand an agent a narrow, current input pack; (4) quality gates that decide pass/fail by script instead of by the model (impl-check, epic-check plan/side-effect/metric checks, result-contract validators with evidence check, model probe); (5) run supervision and runtime hygiene (opencode-aiforge launcher, session-end, session-watch + digest, recycle, host-sample, oac-config); (6) reporting and visibility (run-log comment, run counter, hand-over mirror, Grafana feeds); (7) launchers, secret handling and ops (copilot-*, claude-*, mcp-*, per-project launchers, n8n-shrink-db, legacy github-project-ai). Common design: almost every helper ends with one machine-readable last line (AIFORGE <json>) and mostly exits 0; context builders and reporters fail open (never stop the run), gates fail closed with explicit reasons; every new automation is rolled out in modes off/observe/act; verdicts on measurable facts come from scripts, not from the model. Status seen today: n8n call sites exist for triage, resume-check, project, issue, comment, runlog, epic-context, epic-check (context and pr), epic-delta, epic-pr (via routing_rules.handover_command), review-context, impl-check (via routing_rules.check_command), session-watch (via the launcher's detached watcher) and the launcher itself. systemd timers are enabled only for host-sample and sync-runs; session-watch.timer and github-project-ai.timer are disabled; the n8n node that called opencode-recycle is disabled and unconnected; handover-sync, triage --sweep, triage-switch, model-probe, oac-config, start and n8n-shrink-db have no scheduler or caller (manual tools).

## 7. Externe KI-CLIs, tmux-Sessions und Modell-Routing

The pipeline runs unattended AI agents as external CLI processes. Today the live path is: n8n (Coding workflow) claims a queue item, creates a git worktree per run, renders a versioned DB prompt into .aiforge/run/system.md + user.md, creates a Codeman 'shell' session (a tmux session on a dedicated tmux socket) in that worktree and types one composed command: `cd <worktree> && AIFORGE_*=... OPENCODE_CONFIG_CONTENT=... opencode-aiforge --model <provider/model> [--agent opencoder-pipeline] --prompt "$(cat user.md)"`. The launcher isolates config (own XDG dir, only a GitHub MCP, bot identity, secrets from vault-rendered env), starts OpenCode, keeps a per-run TMPDIR, reports sessionEnd exactly once even after SIGKILL, and can restart OpenCode in the same directory when a watchdog says so. A plugin inside OpenCode (aiforge-hooks.js) streams run events and tool calls to n8n (events, loop guard), pins the model on every message, aborts hung or rate-limited turns, and nudges once when a turn ends without a usable result. Model choice is a Run Profile -> cluster -> ordered endpoint list with health 'cooling', source blocks, one-run-per-model slots, a global cap and a recovery chain (retry same, next model, fallback cluster, Claude Sonnet, give up with human hand-off). All model traffic of the company models goes through LiteLLM (thin aliasing/retry/telemetry gateway; no budgets or fallbacks configured), with FreeLLMAPI behind a 'free-pool' alias. Usage is captured outside the terminal layer: an adapter tails opencode.db into telemetry.usage, LiteLLM/OpenRouter/Claude Code send OTel, and Grafana (AI Usage, AI Pipeline Control Center, Server load) reads Postgres. A Writing path (typed prompts into Codeman terminals, scraped ready-markers, Claude Code/Copilot/OpenCode launchers, resume by CLI family) still exists next to it. The owner's own 2026-11-15 handover (/home/orologas/codeman-cases/testcase/handover-eigenstaendiges-pipeline-tool.md) already frames the target: an AgentRunner interface (tmux+CLI or API), model clusters/fallback/quota/health as configuration, deterministic result validation, and a decision log for every automatic decision.

**Schmerzpunkte und Lehren**

- `opencode --continue` resumes the most recent session of the WHOLE data directory, not of the working directory: with parallel runs a resumed run attached to another issue's session and received its prompts (Netrats#39/#50 landed in #40, 2026-11-02). Fix: always resolve the session by directory (opencode-aiforge last_session). Product: resume must be keyed by run lineage + workspace, never 'latest'. (/home/orologas/docs/opencode-run-profiles.md)
- The OpenCode TUI keeps the model of the resumed session and ignores --model, so a changed Run Profile silently ran the old model (Netrats#38, runs 210/211). Fix: pin the model on every user message via the plugin; the UI footer can still show the old model. Product: record the model per message/turn and enforce the selected model at the adapter.
- SIGTERM from the session host makes OpenCode emit session.idle before exiting, which looked like a normal finish and started gate checks and follow-up runs for a run somebody had just stopped (Netrats#38/#39). Signal handlers inside the plugin do not work (it is not in the main thread). Fix: 2.5 s grace before agentStop, sessionEnd from the launcher. Product: separate 'turn finished' from 'process ended', and make 'ended' an authoritative signal.
- A watcher that is a child of the launcher dies when the host kills the process tree, so no sessionEnd arrived and the issue stayed ai:processing forever (Netrats#40 ended by hand). Fix: setsid inside a subshell + marker-file claim so exactly one of two reporters sends. Product: run-end reporting must survive SIGKILL of the runner's whole group.
- OpenCode waits hours in a silent 'retry' state after a provider usage limit ('retrying in 7h') and a model request can hang with no error (seen with DeepSeek): nothing reaches the engine and the run hangs. Fix: plugin aborts on limit text or waits > 10 min, stall guard and runtime limit per action. Product: every stage needs liveness and time-box limits, and provider retry waits must not count as progress.
- Provider stream aborts depend on prompt size: AI Hub aborted ~10 % of DeepSeek requests at 25-75k prompt tokens and ~33 % at 75-125k (LiteLLM spend logs 30-31 Oct); a 70k cap cut aborts from ~100/day to near zero, but at 70k with ~48k fixed system/tool overhead Copilot compacted every ~10 calls (134 compactions in 15 sessions for Netrats#38 with no progress). On 2026-11-09 the author doubled Qwen to 140k (compaction at 70k broke gap analysis and slicing) and later DeepSeek too (backup opencode.jsonc.bak-20261111-deepseek140k). Docs and file comments still say 70k. Product: context window per model is measured configuration with a documented trade-off, not a constant. (/home/orologas/bin/copilot-squad header, opencode.jsonc comments)
- Long text written in one tool call is lost completely when the stream breaks mid-call (6 of 17 failed sessions in 24 h) and very long answers hit the output limit. Mitigation: write-in-sections rule (opt-in because Qwen rejected an additional system block). Product: prompt guidance + output-limit awareness belong to the adapter; partial writes should be recoverable.
- Qwen via the AI Hub accepts a single system message at the start: plugins adding system prompts, Claude Code's mid-conversation system messages and extra system blocks caused HTTP 400 'rejected as invalid by the model provider'. Shims: merge-system plugin, CLAUDE_CODE_MODEL_CAPABILITIES, drop_params. A Claude Code update can add new mid-conversation features that must be added to the switch list. Product: per-model capability flags and a smoke run after every plugin/CLI upgrade.
- Copilot CLI sends a non-disableable 'sentiment' call to model name gpt-5.4-nano; without an alias it fails. Lesson: CLIs call hidden auxiliary models; the gateway needs aliases for them and usage accounting must include them.
- OpenCode (Bun single binary) unpacks ~14 MB native libs into TMPDIR on every start and never removes them: 490 files / 3.7 GB in /tmp by 2026-11-09. Fix: per-run TMPDIR removed at exit (and by the detached watcher after SIGKILL). Product: give every run its own scratch dir and delete it.
- The shared `opencode serve` kept ~250 MB per finished session and burned more CPU over time (309 MB -> 3.3 GB after ~10 sessions, 136 % CPU on 2026-11-08). Mitigations: idle-only recycle with advisory lock + drain, then the architectural fix of one OpenCode process per run in its own session. Product: prefer process-per-run; if a long-lived server is unavoidable, include drain/recycle.
- opencode.db grew from 2.2 GB to 15 GB and filled the root disk (2.3 MB free on 2026-11-18); the emergency VACUUM INTO itself failed with 'database or disk is full'. Fixes: 12 h retention every 15 min, incremental auto_vacuum, snapshot/tool-output/log cleanup, DB compaction script. Product: agent-tool stores need retention from day one and an emergency path that does not need extra disk.
- (Inferred, evidenced) Retention is currently stalled: since ~2026-11-19 the log shows 'N Sessions noch nicht in telemetry.usage -> uebersprungen' growing from 3 to 399 and 'geloescht=0' on every 15-min run, permanent emergency mode (free 3.6 GB < 6 GB), DB back to 1.0 GB and rising. Likely cause: retention.py requires telemetry.usage rows with source='opencode', while the deployed adapter (dist/sync.js built 2026-11-18) skips every message whose provider is not 'opencode' (AI Hub/OpenRouter usage is booked via LiteLLM/OpenRouter), so sessions that used only those providers can never be deleted. Lesson: a deletion safety net must check 'usage captured anywhere', not 'captured by one specific ingestor'. (/home/orologas/.local/share/opencode/retention.py, retention.log; /home/orologas/repos/telemetry/opencode-adapter/src/sync.ts)
- A second, older cleanup (opencode-scheduler job: delete sessions older than 6 h, no telemetry check) exists with an enabled-but-inactive timer; the cleanup.sh script drops nearly all tables. Several competing cleanup mechanisms = confusion and data-loss risk. Product: exactly one retention owner.
- Prompts are visible in the process list (opencode --prompt ...), so `pkill -f <text>` from one agent killed another run's OpenCode (gate of #127 killed by the agent of #129). Fix: plugin blocks pkill/killall; agents may only kill PIDs they started. Related: secrets in argv leak to `ps` (an earlier Vercel-Blob token; at analysis time a postgres MCP helper started from an interactive Claude session shows its connection string with credentials in its command line - value not reproduced here). Product: never pass secrets or long prompts as argv; use env/files and process names that do not collide.
- Agents and services share one tmux server, so exported variables leak into agent sessions; the owner deliberately keeps tokens out of codeman-web/tmux env and uses a pipeline-mode agent that denies curl/sudo/.env access. Product: sandbox each run (container or user namespace) rather than relying on rules; Codeman sessions are not a security boundary.
- Agents wrote invalid JSON hand-over files (unescaped quotes) and only failed at the very end. Fix: validate .aiforge/*.json on write and return the parse error to the model immediately. Product: validate contract artifacts at write time.
- Turns ended without a usable result (empty answer, output limit, 'next I will...' without tool call, expected file missing). Fix: one automatic nudge. Product: bounded automatic follow-up before declaring failure.
- Loop guard false positive: running the same lint/test script after every atomic edit was blocked (Netrats#38). Fix: a file edit resets the counter for non-edit calls. Models also ignore denials, hence the abort escalation after the 3rd denial. Product: progress-aware loop detection.
- Comment pagination trap: the GitHub MCP returns 30 comments (oldest first); models read page 1 and reported 'no new comments' although decisions were on page 2 (Netrats#38). Fix: force page size 100 and append a 'fetch next page' hint; AGENTS.md also instructs reading all pages. Product: tool wrappers should rewrite arguments and annotate partial results.
- Terminal-driven control is fragile: ready detection by scraping buffer strings ('ctrl+p commands', 'bypass permissions on'; whitespace removed because the buffer drops spaces), first-run trust dialogs, Copilot swallowing \r with fast input, Claude/OpenCode submitting on every newline (prompt as one line, Enter after 2 s), shell-mode 'idle' firing only once, Codeman rejecting names > 100 chars. Fix in Coding path: prompt via file + --prompt and confirmation by a plugin event. Product: prefer structured launch/prompt channels (stdin/args/API) and event-based readiness over screen scraping.
- Model health logic gaps (owner's own audit 2026-11-05): only two error texts classify as blocks, 429/5xx/timeouts are indistinguishable; blocks are per SOURCE (a Zen free-limit blocks all Zen models in all clusters); no half-open probe; 'cooling-fallback' still starts a blocked model when everything is cooling; the recovery override is not re-checked; verify_score, data_policy and max_parallel are never read; errors are attributed via sessions.launcher so sessions sharing one copilot_session_id or ~20 simulated test errors skew counters; the trigger swallows exceptions; quota counters exist only for openrouter-free. Operating snapshot then: DeepSeek on AI Hub 31 of 51 sessions failed (30 recoveries) vs Qwen 0 of 37, though numbers are inflated by the join issue. Product: classify errors (rate limit, overload, outage, quota, content), keep history of blocks, make capability/quality fields effective or remove them.
- Free tiers are not stable or private: Zen free daily limits are unpublished and varied (~290 to 678 requests/day), Google free quota was exhausted by 4 requests/117k tokens in 25 s (RPM/TPM/RPD indistinguishable), Gemini free tier trains on data (data_policy 'trains') and the runs load the author's private knowledge files; free-pool prompts go to third parties. Product: data-policy metadata must gate which cards may use which models.
- Concurrency: two OpenCode sessions with the same model 'led to chaos', and the 4-core host is the real limit (max_active_runs 2). Product: per-model exclusivity and a global cap are required defaults; show queue reason (global-cap, model busy).
- Run lifecycle bookkeeping must happen BEFORE the effect: the session row is registered before launch (so first hook events resolve), the old session row is closed before its Codeman session is deleted (so the kill is not read as run end), the stale run's Codeman session is deleted before resuming the same conversation id (agent must release its session lock; +3 s sleep). Product: order operations so that events always find their run.
- Silent failure history: swallowed hand-over errors, trigger exceptions and plugin failures are all fail-open by design; the owner's rule is 'never swallow errors silently: decision log + visible comment'. Product: every automatic decision (recovery, nudge, restart, block) gets a logged reason.
- Cost data model complexity: five different code paths wrote shadow_cost (22,438 rows had shadow cost without entity/pricing link; a 72k-record repair was needed); actual_cost is mostly NULL; LiteLLM cost is 0 for company models; usage rows for OpenCode arrive without tokens first and are filled at completion (refresh window needed). Product: one canonical usage event with explicit provenance fields and one pricing resolver.
- Single-trigger ingestion broke when the architecture changed: the adapter initially relied on SSE from `opencode serve`; once runs became separate processes it needed inotify on the DB files. Product: capture usage from the durable store or gateway, not from a long-lived server's event stream.
- Configuration drift: docs say DeepSeek 70k while config says 140k; LiteLLM retries 2 (doc 11-05) vs 4 now; run-profiles doc and code disagree on pause semantics; many .bak files, plugin backups and dangling skill symlinks pointing into /tmp/opencode/litellm-skills; the Writing and Coding paths use different launch mechanics (typed prompts vs --prompt file). Product: one source of truth per setting, versioned, with change history.
- Owner-documented operational limits not yet tested end-to-end: loop-guard denial, compaction at length, recovery after stopFailure inside n8n, the merge-agent full run; the pipeline has no automated test suite (audit 2026-11-09 section 6). Product: simulate failures (kill, hang, quota, abort) in tests.
- The agent frameworks themselves are interactive by design: OAC agents require approval gates and ask permissions, which would stall unattended runs; the adapter script asserts each text replacement and refuses to build if upstream changed. Product: if third-party agent definitions are reused, an adaptation layer with fail-closed checks is needed.
